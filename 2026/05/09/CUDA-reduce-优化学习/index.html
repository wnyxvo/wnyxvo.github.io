Reduce 的本质：把 N 个元素，使用某种结合运算（+ / max / min / xor …）， 最终压缩成更少元素。

baseline

树状折半规约:

潜在的问题:

  • 线程闲置：在规约阶段（for 循环中），随着迭代的进行，参与计算的线程数逐次减半，导致大量线程在整个归约过程中始终处于空闲状态，甚至有部分线程从始至终都没有执行过任何有效计算，是参与计算的线程数过少。

  • 线程束分化 Warp Divergence：

    线程束分化（Warp Divergence） 是 GPU 并行计算（尤其是 CUDA 架构）中一个极其关键的性能瓶颈概念。简单来说，当一个线程束（Warp，通常包含 32 个线程）中的线程在执行代码时，由于逻辑分支（如 if-else、switch 或 for 循环次数不同）走向了不同的指令路径，就会发生分化。

    GPU 使用的是 SIMT（Single Instruction, Multiple Thread），对应的一个 warp 的 32 个线程在同一时刻执行同一条指令。但是如果存在分支代码（if/else），一部分线程走 if，另一部分走 else，会导致执行if时会有一部分线程在空等，warp 内分叉非常严重。

    在一个 warp 中大量的线程是 idle 的

  • 存储体冲突(bank conflict)：

    共享内存被划分为 32 个独立 Bank（SM 为 32），每个 Bank 每周期只能服务 1 次访问

    按 4 字节（int/float） 对齐，地址映射公式：bank_id = (byte_addr / 4) % 32。连续的 4 字节为一组被映射到 Bank 0 到 Bank 31，循环映射。

    示例（__shared__ int s[]）：

    • s[0] → bank 0
    • s[1] → bank 1
    • …
    • s[31] → bank 31
    • s[32] → bank 0（循环）

    当同一个 Warp（32 线程）内多个线程同时访问同一个 Bank 的不同地址时，访问会被串行化，带宽急剧下降

    广播例外：多线程读同一地址 → 硬件广播，无冲突

    当 s == 16 且 tid == 0 时，线程会访问 s[0] 和 s[16]；而当 tid == 1 时，则会访问 s[32] 和 s[48]。这种访问模式导致了 s[0] 和 s[32] 等地址之间出现 bank 冲突，因为它们映射到了相同的共享内存 bank。也就是说不同的线程tid = 0, tid = 1在同一时间访问了同一个bank，也就是s[0]和s[32]所在的bank。

  • 取模运算对于GPU来说消耗太大

index-based addressing

优化点 ：warp divergence 和 modulo 指令开销

还没有解决：shared memory bank conflict

index = 2 * s * tid

本质：不再让所有线程都参与条件判断；而是：只让“可能工作的线程”去访问目标位置。

尽可能让活跃的 thread 都在 同一个 warp 内，减少了线程束分化

shared memory bank conflict 更严重了：

在第一次迭代中，0号线程需要去加载 shared memory 的0号和1号地址，然后写回0号地址。此时，0号 warp 的16号线程需要加载 shared memory 的32和33号地址并且写回32号地址。所以，我们在一个warp内同时访问了一个bank的不同内存地址，发生了2路的 Bank Conflict。

s = 1，warp 0 内 thread0 访问 sdata[0] sdata[1]，thread16 访问 sdata[32] sdata[33]，造成2-way bank conflict

s = 2，warp 0 内 thread0 访问 sdata[0] sdata[2]，thread8 访问 sdata[32] sdata[34]，thread16 访问 sdata[64] sdata[68]，thread24 访问 sdata[96] sdata[100]，造成4-way bank conflict

以此类推，下一次迭代会产生8路的 Bank Conflict，使得整个 Kernel 一直受到 Bank Conflict 的影响。

s = 16，warp 0 内每个 thread 都访问 bank0，出现 32-way bank conflict

Sequential Addressing

s = 1，warp 0 内 thread0 访问 sdata[0] sdata[128]，thread1 访问 sdata[1] sdata[129]…warp0 的线程刚好加载shared memory的一行数据，不会产生 bank conflict

s = 2，warp 0 内 thread0 访问 sdata[0] sdata[64]，thread1 访问 sdata[1] sdata[65]…加载shared memory的一行数据，不会产生 bank conflict

解决 idel 线程：First Add During Load

当前版本的 kernel 浪费了大量的线程。对于第一轮迭代只有128个线程在工作，而第二轮迭代只有64个线程工作，第三轮迭代只有32和线程工作，以此类推，在每一轮迭代中都有大量的线程是空闲的。

数据加载模块进一步优化

之前版本的搬运数据阶段，每个线程都只从全局内存搬运一个元素到共享内存中。 但是实际上我们可以每个线程多读取一点，例如一口气读取两个元素，并且可以直接在本地寄存器里把它们加起来。

注意这里全局下标的步长已经不是blockDim.x，而是对其乘以2。 这就意味着同样数量的线程，v3覆盖的数据是v2的两倍，这意味着Block的数据可以减半。

提升了计算密度。寄存器的带宽远超共享内存，并且没有bank conflict，线程在等待全局数据内存的同时就可以做这件加法。

为什么一次不读4个、8个？

当然可以，而且很多高性能库就是这么干的。但是增加单线程的负载同时也会减少活跃的线程块数，可能降低硬件占用率。因此需要在“每线程工作量”和“并行度”之间找到一个平衡点。v3 的 ×2 只是一个讨巧的起步优化。

展开最后一个 warp

为什么需要展开最后一个 warp？

即使只剩一个 warp，仍然 __syncthreads()，但 warp 内本来就同步，这是 GPU 硬件保证的。warp 内：SIMT lockstep execution、指令天然同步，所以warp 内不需要 __syncthreads()。

从Volta 架构 (SM 7.0)开始，NVIDIA 引入了独立线程调度 (Independent Thread Scheduling)，彻底打破了传统的 “warp 同步执行” 假设

__syncthreads() 非常昂贵

它本质上是block-wide barrier，SM 要：

  • 等待同一 block 内的所有 warp
  • flush dependency
  • scheduler stall

unroll last warp 优化了：

  • 去掉了__syncthreads()
  • 减少了 loop overhead，每次 for 循环也是需要开销的
  • 减少了 branch divergence，s = 16时，warp0 中已有thread0~15是活跃的

为什么用了 volatile？ 防止编译器寄存器缓存。

编译器会做一种非常激进的优化：把频繁访问的共享内存变量缓存在寄存器里。这会导致编译器认为寄存器中的值就是最新值，实际上不是。

加上这个关键字之后，编译器不再对 cache指向的地址做任何寄存器和缓存优化。每一步累加都从共享内存里取最新的数据，算完再立刻写回去。warp 内部的线程能保证它们看到彼此的最新写入，计算也就完全正确了。

在CUDA编程中，volatile核心作用就是强制编译器每次从显存中读取变量，以避免因为优化导致的数据不一致问题。

一般来说它是为了进行跨线程通信与阻止编译器优化。

注意：volatile并不等于同步或者原子操作。如果多个线程并发写，那么仍然会产生数据竞争。它并不能保证原子性与顺序。

完全展开循环

之前的版本 ：

v4中实际上仍然采用了for循环来进行规约。这是属于运行时循环，每次迭代GPU和CPU都需要做以下操作：

  1. loop branch
  2. compare
  3. shift
  4. jump

现在 模板+编译期常量展开，blockSize 是 template parameter。

例如 reduce_v5<256>，编译器看到：if (256 >= 512)，会直接将 “512段代码” 删除，最终生成的 SASS/PTX：

这种方法去掉 loop overhead，编译器 instruction scheduling 更容易。

本质上：不是 runtime if，而是：compile-time specialization。完全展开循环默认了BLOCK_SIZE必须是2 的整数次幂，所有的if (BLOCK_SIZE >= X)判断都是为了在编译时根据块大小生成对应的归约步骤。用代码尺寸换性能。

GPU optimization 本质之一：给编译器更多静态信息。template 就是这样，template 能把 runtime 信息变 compile-time 信息。这是 CUDA 高性能代码核心。

warpReduce_v5是：warp-synchronous reduction，不需要 __syncthreads()。

AI kernel 的一个核心思想：尽量把通信限制在 warp 内，因为 warp 内：synchronization free

Grid Loop

核心思想：让每个线程处理多个元素，每次跳过当前 grid 中所有线程一次能处理的元素总数。

为什么需要 grid loop：block 中每个线程一个处理的数据量太少，当数据量 N 很大是，就会需要海量的 block。但是由于 SM 硬件数量有限，就意味着绝大多数 block 都在排队。导致 kernel launch overhead、block scheduling overhead 开销过大。

v6 的核心思想就是 thread reuse，一个线程会循环处理多个元素。

本质：用较少 block 覆盖整个数据集
