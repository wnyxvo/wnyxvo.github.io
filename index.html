Query Plan

  1. 从 SQL 到查询计划：数据库系统接收到 SQL 语句后，并不会直接执行，而是先通过查询优化器将其编译成一个查询计划。这个计划就像一份详细的“执行说明书”。

  2. 操作符树：查询计划是一个树形结构（操作符树）。每个节点代表一个基本操作（称为操作符或代数运算符），例如：

    • 叶子节点：Table Scan（全表扫描）、Index Scan（索引扫描），负责从磁盘中读取数据。
    • 内部节点：Filter（选择，即 WHERE 子句）、Project（投影，即 SELECT 字段）、Join（连接）、Sort（排序）、Aggregate（聚合，如 GROUP BY）。
    • 数据从叶子节点流向根节点，在每个节点进行相应的处理，最终在根节点得到查询结果。

  3. 磁盘导向与缓冲池：因为数据量远大于内存，数据库必须聪明地管理数据在内存和磁盘之间的移动。缓冲池就是核心组件，它充当了磁盘数据在内存中的“缓存”。

    • 当操作符需要处理数据时，它向缓冲池请求特定的页。如果页已在缓冲池中（缓存命中），则直接使用，这是最快的访问方式。
    • 如果页不在缓冲池中（缓存未命中），则需要从磁盘读取，这会带来昂贵的 I/O 成本。
    • 缓冲池需要决定将哪个旧页替换出去（例如使用 LRU 算法）。

  4. 核心目标：最小化 I/O：由于磁盘 I/O 比内存操作慢几个数量级，查询执行算法的设计核心就是尽可能减少磁盘 I/O 次数。这体现在：

    • 访问方法：使用索引（如 B+Tree）来避免全表扫描。
    • 连接算法：使用更高效的算法（如基于哈希的连接、排序-合并连接）来减少中间结果的读写。
    • 利用缓冲池：良好的缓存命中率能极大提升性能。

为了“最小化 I/O”，数据库为不同的操作符设计了特定的算法：

  1. 连接操作：

    • 嵌套循环连接：简单但 I/O 成本可能很高（O(M*N)）。
    • 排序-合并连接：先对两个表按连接键排序，然后进行归并。如果数据能装入内存，效率很高；否则需要外部排序，会产生中间文件的 I/O。
    • 哈希连接：通常效率最高。为其中一个表构建内存哈希表，然后探测另一个表。如果表太大，会采用Grace Hash Join等方法进行分区并溢出到磁盘。

  2. 排序操作：

    • 外部排序：当待排序数据远超内存大小时使用。算法（如外部归并排序）将数据分块排序后写入磁盘，再将有序块归并起来。其 I/O 成本是衡量性能的关键。

  3. 聚合操作：通常使用排序或哈希在分组时进行，同样需要考虑数据是否能放入内存。

数据库查询执行的核心路径：

SQL 查询 -> 查询编译/优化 -> 查询计划（操作符树）-> 由执行引擎调用操作符的具体算法执行 -> 算法依赖缓冲池在内存和磁盘间交换数据 -> 所有设计的首要目标是最小化慢速的磁盘 I/O。

Sorting

关系模型中的表是无序的集合。为了满足 ORDER BY、GROUP BY、JOIN（如排序-合并连接）、DISTINCT等操作对数据有序性的要求，排序是必不可少的。

当数据可以完全放入内存时，可以使用内部排序算法，如快速排序。当数据太大无法放入内存时，需要使用外部排序，例如外部归并排序，它能够将数据溢出到磁盘，并优先使用顺序I/O而不是随机I/O。

Top-N 堆排序

它是对 ORDER BY ... LIMIT N查询的极致优化。

  • 场景：查询只需要结果集中的前 N 条（或后 N 条）记录。
  • 数据结构：使用一个堆（优先队列）。
    • 求前 N 个最小值：使用最大堆。堆顶是堆中最大的元素。新元素如果比堆顶小，则替换堆顶并调整堆。
    • 求前 N 个最大值：使用最小堆。堆顶是堆中最小的元素。新元素如果比堆顶大，则替换堆顶并调整堆。
  • 过程：只需单次扫描数据。对于每条记录，与堆顶元素比较，决定是否替换并调整堆。扫描结束后，堆中剩下的就是 Top-N 结果。
  • 优势：极低的内存占用：只需维护一个大小为 N 的堆，无论总数据量有多大。单次扫描，线性复杂度：算法复杂度为 O(M log N)，其中 M 是总记录数，N 是 LIMIT 值。这比先全排序（O(M log M)）再取前 N 条要高效得多。

外部归并排序 - 通用大数据集排序

这是处理海量数据排序的标准算法，其核心思想是 “分而治之”，分为两个主要阶段：

阶段一：排序阶段

  • 步骤：将大数据集分割成多个小块（称为 Runs），每个小块的大小恰好能放入内存的缓冲池中。
  • 操作：逐个将每个 Run 读入内存，使用高效的内部排序算法（如快速排序）对其进行排序。
  • 输出：将每个在内存中排好序的 Run 作为临时文件顺序地写回磁盘。
  • I/O 优势：无论是读原始数据还是写临时 Run，都追求顺序 I/O，这比随机 I/O 快几个数量级。

阶段二：归并阶段

  • 步骤：将多个已排序的 Run 归并成一个更大的有序文件。由于内存有限，通常采用 K-路归并。
  • 操作：同时打开 K 个已排序的 Run 文件（K 受限于内存缓冲区数量）。为每个文件在内存中维护一个缓冲区，每次从 K 个 Run 的当前值中选出最小（或最大）的一个输出到最终结果，并补充该 Run 的下一个值。
  • 迭代：如果一次 K-路归并后仍然有超过一个 Run，则重复此过程，直到所有数据归并到一个完整的有序文件中。

两路外部归并

核心特点：

  • 每次只归并2个有序段
  • 需要3个缓冲页：2个用于输入，1个用于输出
  • 简单但效率相对较低

过程分解：

排序阶段：读取每个页面 → 内存排序 → 写回有序段
归并阶段：反复两两归并，直到完全有序

I/O成本分析：

  • 趟数（Passes）：1 + ⌈log₂N⌉
  • 总I/O操作：2N × (1 + ⌈log₂N⌉)
  • 示例：N=1000页时，需要1+10=11趟，22,000次I/O操作

通用K路归并排序

N: 文件占用的总页数 (total number of pages in the file)。

B: 内存中可用的缓冲区页数 (number of buffer pages in memory)。

核心优化思想：

  • 利用更多缓冲页：一次性归并K个有序段（而不仅仅是2个）
  • 减少归并趟数：K越大，需要的归并趟数越少
  • 最大化顺序I/O：仍然是批量读写，避免随机访问

策略：

可用缓冲页总数：B ；1个页面用于输出缓冲区 ；剩余B-1个页面用于输入缓冲区（每个归并段占用1个）；∴ 最大归并路数K = B-1

排序阶段：

由于总共有 N 页数据，每次处理 B 页，所以总共需要 N / B 次这样的操作。因为最后一次可能不足 B 页，所以严格来说，会生成： ⌈N / B⌉ 个初始有序顺串，每个顺串的大小（除了最后一个）为 B 页。

归并阶段：

现在有 ⌈N / B⌉ 个有序的顺串在磁盘上。下一步是把它们合并成一个单独的、完全有序的文件。利用缓冲区来同时合并多个顺串。

  • 操作: 在 B 个可用的缓冲区中，必须留出 1 页作为**输出缓冲区 (Output Buffer)**，用来存放归并的结果。
  • 处理: 剩下的 B-1 页缓冲区，则作为**输入缓冲区 (Input Buffers)**，每一页对应一个要被合并的顺串。
  • 归并: 这意味着每一轮归并，最多可以合并 B-1 个顺串。这就是所谓的 (B-1)-way merge。
  • 循环:
    • Pass #1: 将 ⌈N / B⌉ 个顺串，每次 B-1 个进行合并。这一轮结束后，顺串的数量会减少为 ⌈ (⌈N / B⌉) / (B-1) ⌉ 个，但每个顺串的长度变得更长。
    • Pass #2: 对 Pass #1 产生的新顺串，再次进行 (B-1)-way merge。
    • …: 持续这个过程，直到最后只剩下 1 个顺串，即整个文件完全有序。

总趟数 = 初始排序的趟数 () + 归并的趟数。

  • 排序趟数: 占了 1 趟。
  • 归并趟数: 需要计算，从 ⌈N / B⌉ 个初始顺串开始，需要多少轮 (B-1)-way merge 才能合并为 1 个顺串。
    • 这是一个对数问题：$\log_{B-1}(初始顺串数量)$
    • 代入初始顺串数量，归并趟数即为 $\log_{B-1} ⌈N/B⌉$。

推导结果: 将两者相加，总趟数 (Total number of passes) 即为：1 + $\ ⌈log_{B-1} ⌈N/B⌉⌉$

总 I/O 成本: 计算总共发生了多少次磁盘页的读或写。

  • 关键假设: 在每一趟归并躺中，文件中的每一页 (N) 都必须被从磁盘读取一次，然后被写回磁盘一次。每趟成本: N (读) + N (写) = 2N 次 I/O。

推导结果: 总 I/O 成本 = (每一趟的 I/O 成本) × (总趟数) Total I/O Cost = 2N ∙ (# of passes)

将上面推导的趟数公式代入，总成本的完整表达式为： 2N * (1 + $\ ⌈log_{B-1} ⌈N/B⌉⌉$ )

双缓冲优化

双缓冲优化通过预取（prefetching）下一个数据块（run）来减少I/O等待时间。具体来说，当系统正在处理当前数据块时，使用另一个线程在后台预取下一个数据块，并将其存储在第二个缓冲区中。这样，当当前数据块处理完成后，可以立即开始处理下一个数据块，而不必等待I/O。

实现方式：

  • 使用两个缓冲区：一个用于当前处理，一个用于预取下一个数据块。
  • 需要多线程：一个线程处理当前数据块，另一个线程在后台预取下一个数据块。

对比优化

代码特化（Code Specialization）

消除函数调用开销；启用内联优化；更好的指令缓存局部性。

后缀截断（Suffix Truncation）

特别适用于：

  • 长字符串键（VARCHAR、TEXT）
  • 前缀区分度高的数据（如UUID、哈希值）

对于字符串类型的比较，如果键很长，比较操作可能很昂贵。后缀截断优化是：首先比较长字符串的二进制前缀（例如，前几个字节），如果前缀不同，就可以快速得出比较结果；如果前缀相同，再调用完整的字符串比较。这类似于在数据库索引中使用的前缀压缩。

B+树排序

如果需要排序的表已在排序属性上创建了B+树索引，则可利用该索引加速排序过程。

聚簇索引

定义和特点

  • 数据即索引：叶子节点直接包含完整的表数据行
  • 物理有序：数据行按照索引键的顺序物理存储在磁盘上
  • 唯一性：每个表只能有一个聚簇索引

劣势

  • 插入性能：需要维持物理顺序，可能引起页分裂
  • 更新代价：更新索引键可能导致数据移动
  • 灵活性差：每表只能有一个聚簇索引

非聚簇索引

定义和特点

  • 索引与数据分离：叶子节点包含索引键和指向数据行的指针（如聚簇索引主键或物理行指针）
  • 物理无序：数据行物理存储顺序与索引键顺序无关
  • 多索引支持：每个表可以有多个非聚簇索引

核心概念对比

特性 CLUSTERED B+TREE UNCLUSTERED B+TREE
数据存储 索引即数据，叶子节点包含实际数据行 索引与数据分离，叶子节点包含数据指针
表数量 每表只能有1个 每表可以有多个
物理顺序 数据按索引键顺序物理存储 数据物理存储顺序与索引无关
查询性能 范围查询和排序高效 点查询高效，范围查询需要回表

Aggregations

聚合操作 的本质是将一组行（元组）根据某个或某几个键（GROUP BY key）分类，然后对每一类计算一个汇总值（标量值），例如 COUNT、SUM、AVG 等。

两种实现路径：数据库管理系统（DBMS）主要通过两种物理操作来实现这个逻辑概念：排序聚合 和 哈希聚合。查询优化器会根据数据量、内存大小、是否需要有序输出等因素选择最佳路径。

排序聚合

原理解释

这种方法非常直观，分为两步：

  1. 排序：首先，将所有数据按照 GROUP BY的键进行排序。这就像把一堆杂乱无章的卡片先按花色和点数排好序。内存排序：如果数据量小，可以直接在内存中用快速排序等算法完成。外存排序：如果数据量超过内存（缓冲区）容量，则使用外部归并排序算法，这是一种分批排序再归并的算法，能够处理海量数据。
  2. 扫描计算：排序后，所有相同键的元组会紧挨在一起。此时，DBMS 只需顺序扫描数据，每当遇到一个新的键，就知道前一个键的所有数据已经处理完毕，可以输出聚合结果了。

特点与优化

  • 输出有序：最大的优点是聚合结果的输出自然就是按照分组键排序的。如果查询后面有 ORDER BY子句，并且排序键和分组键一致，那么这个排序成本就省掉了。
  • 优化策略：“筛选下推”。这是非常重要的优化原则。在执行聚合排序前，应尽早使用 WHERE条件过滤掉不相关的数据行。这样可以显著减少需要排序的数据量，降低 I/O 和 CPU 开销。

拓展：适用场景

  • 当查询最终需要有序输出时（例如后面有 ORDER BY ...）。
  • 当数据本身已经接近有序或有合适的索引时（例如，在分组键上有索引，数据库可能直接使用索引来避免排序）。
  • 当需要产生支持排序的中间结果，以供后续查询操作（如 Merge Join）使用时。

哈希聚合

原理解释

哈希聚合不进行排序，而是利用哈希表的高效查找特性（平均 O(1) 时间复杂度）来实时计算聚合值。

  • 基本思想：DBMS 一边扫描数据，一边维护一个临时哈希表。这个哈希表的键是 GROUP BY的键，值是一个运行值，用于记录当前的聚合状态。
  • 处理过程：对于每一行数据，计算其分组键的哈希值，然后在哈希表中查找：命中：如果找到相同的分组键，则直接更新该键对应的“运行值”（例如，COUNT加 1，SUM加上新值）。未命中：如果没找到，则在哈希表中插入一个新的条目（分组键 -> 初始运行值）。

处理大数据集的分阶段（混合哈希）策略

当数据量巨大，哈希表无法完全放入内存时，DBMS 采用一种“分而治之”的策略，通常包含两个阶段：

阶段一：分区

  • 目标：将大数据集分解成多个能放入内存的小分区。
  • 方法：使用一个哈希函数 h1 将元组分散到不同的磁盘分区中。关键点在于：相同分组键的元组一定会被散列到同一个分区。
  • 内存管理：假设有 B 个内存页（缓冲区），DBMS 会拿出 1 页来读取输入数据，剩下的 B-1 页分别作为 B-1 个分区的输出缓冲区。当某个缓冲区分区页满了，就将其写入磁盘。最终，原始数据被分割成 B-1 个磁盘文件（分区）。

阶段二：再哈希

  • 目标：逐个对分区进行聚合计算。
  • 方法：依次将每个分区从磁盘读入内存。对于分区内的数据，使用另一个不同的哈希函数 h2 在内存中构建一个新的哈希表。然后按照基本的哈希聚合流程处理这个分区内的所有数据。
  • 关键假设：这个策略假设每个分区的大小都能装入内存。由于阶段一确保了同一个分组的所有数据都在同一个分区，因此阶段二可以独立、正确地完成每个分区的聚合计算。

拓展：“运行值”的智慧

  • 哈希表存储的不是最终结果，而是中间状态。这对于不同的聚合函数是不同的：COUNT：运行值就是一个整数，每遇到一个匹配项就加 1。SUM：运行值也是一个数，不断累加。AVG：不能只存一个平均值。运行值通常是一个二元组 (Count, Sum)，最后再计算 Sum / Count。这是一种典型的用空间换准确性的设计。MIN/MAX：运行值就是当前遇到的最小值或最大值。

总结对比与选择策略

特性 排序聚合 哈希聚合
核心步骤 先排序，后扫描 建哈希表，实时更新
输出顺序 有序（按分组键） 无序
内存不足时 使用外部归并排序 使用混合哈希（分区+再哈希）
计算复杂度 O(n log n) **平均接近 O(n)**，更高效
适用场景 1. 需要有序输出 2. 数据已预排序 默认首选，除非需要排序或数据已有序

对于聚合操作，哈希法几乎总是比排序法更高效的，除非数据已经预先排好序，或者查询明确要求有序输出。 因为哈希的平均时间复杂度是线性的，而排序是线性对数的。现代数据库的查询优化器在大多数情况下都会优先选择哈希聚合。

Latches

locks（锁） 和 latches（闩锁） 是两种关键的并发控制机制

特性 Locks (锁) Latches (闩锁)
保护对象 数据库逻辑内容（行、表） 内存物理结构（页、索引节点）
作用范围 事务级别 操作级别（进程、线程）
生命周期 事务期间（秒级） 操作期间（微秒级）
粒度 粗粒度（行/页/表） 细粒度（内存结构）
死锁处理 检测与解决（回滚） 预防（严格顺序）
模式 共享/排他/意向锁等 读/写锁
管理机制 锁管理器 操作系统原语
可见性 用户可见（可查询） 内部实现细节

latch modes:

  • Read mode: 多个线程可以同时读同一个对象；当其他线程在读对象时允许线程获取读锁
  • Write mode: 同一时间只允许一个线程拿到写锁；

latch 要实现的目标：

  • 较小的内存占用
  • 无竞争时快速的执行路径
  • 分布式的闩锁管理机制

  • 第一层：存储所有节点
  • 第二层：存储1/2的节点
  • 第三层：存储1/4的节点

接下来将讨论如何支持 DBMS 的执行引擎从 page 中读写数据。介绍两类结构：Hash Tables(Unordered)、Trees(Ordered)。

Data Structures

在数据库系统中，存储结构的类型可以根据用途划分为以下几大类，它们共同组成了数据库系统的“内部世界”：

  • Internal Meta-Data（内部元数据）：这是数据库系统用于管理自身状态和结构信息的数据。用于记录数据库对象的布局、位置、映射信息等，如页表、页目录等。
  • Core Data Storage（核心数据存储）：这是用来实际存储表中的数据（Tuples）的结构。以页为单位将表的数据组织在磁盘中，如NSM/DSM/PAX、Slotted Page。
  • Temporary Data Structures（临时数据结构）：为了提高查询效率，DBMS 在查询运行时构造的临时结构。如哈希表（用于 hash join 或去重）、排序缓冲区、物化表。这些结构在查询结束后通常会被释放。
  • Table Indices（表索引）：数据库系统为了加速特定查询而维护的辅助数据结构。如 B+ 树索引、哈希索引。索引通常是冗余的，会占用额外空间，但能显著提升性能。

在实现数据结构时还需要考虑以下两个设计决策：数据结构的布局对性能的影响、并发性。

Hash Tables

哈希表实现了一种关联数组抽象类型，能将键映射到值。平均运算复杂度 O(1)，最坏为 O(n)；存储复杂度为 O(n)。即使平均运算复杂度为 O(1)，但仍有常数因子，这在现实世界中非常重要。哈希表中没有访问顺序，即无法按任何特定顺序浏览元素。

哈希表的实现由两部分组成：

  • 哈希函数： 如何将一个大的键空间映射到一个较小的域。在其中要权衡运算速度和冲突率。
  • 哈希方案： 如何处理哈希冲突。在其中要权衡分配哈希表的规模和 get/put 键值的开销

Hash Function

哈希函数接受任何长度的输出，输出固定长度的整数(32bits or 64bits)。DBMS 中不需要使用加密类型的哈希函数（如 SHA-256），只关心速度和冲突率。

现在 state-of-the-art 的哈希函数时Facebook XXHash3。

Static Hash Schemes

Static Hash Schemes 是指哈希表的大小是固定的，并且是已知的。这意味着，如果数据库管理系统的哈希表存储空间用完，就必须从头开始重建一个更大的哈希表，而这是非常昂贵的。通常情况下，新的哈希表是原始哈希表的两倍。

Linear Probe Hashing

对于插入操作，当发生碰撞时，我线性搜索随后的插槽，直到找到开放的插槽为止，必要时会从数组的末尾循环到起始位置。

对于查找操作，可以检查密钥哈希值所对应的插槽，然后进行线性搜索，直到找到所需的条目。如果找到的是空槽，或者遍历了 hashtable 中的所有槽，则说明表中没有该键。请注意，这意味着我们必须在槽中同时存储键和值，以便检查条目是否为所需条目。

对于删除操作：

  • 直接删除会有点问题，如何之前发生过哈希冲突，会有本该映射到此的键值A被映射到了后方，当后续检索A时发现此处为空返回不存在。
  • 另一种方法是在删除条目后移动相邻数据，以填补现在的空槽。不过当键的数量较多时，这种方法的成本极高。
  • 最常见的方法是使用 “墓碑”。我们不是删除条目，而是用一个 “墓碑 ”条目取代它，告诉未来的查找继续扫描。

如何存储键值：

  • 固定长度：直接存储在哈希表页面中。也可选择将密钥的哈希值与之一起存储，以加快比较速度。
  • 不定长度：将键/值数据插入一个单独的临时表中。然后，哈希表将哈希值作为键存储，将指向临时表中相应条目的记录 ID 作为值存储。

如何处理键值不唯一：

  • 独立的链接列表： 不是将值与键一起存储，而是存储一个指向单独存储区的指针，该存储区包含一个包含所有值的链接列表，可能会溢出到多个页面。
  • 冗余键： 更常见的方法是在表中多次存储相同的键。即使我们这样做，线性探测的所有功能仍然有效。

Cuckoo Hashing

Cuckoo Hashing 使用 两个（或多个）哈希函数，每个 key 可以存放在两个可能的位置之一。如果插入的位置被占用了，就“驱逐”（evict）原来的 key，并将其移动到它的另一个位置，可能会引发 连锁搬移。

Cuckoo Hashing 花费 O(1) 的代价查找和删除，但是插入操作可能高代价。

Dynamic Hash Schemes

Dynamic Hashing Schemes（动态哈希方案） 是一类支持数据动态增长（或缩减）的哈希方法，主要为了解决传统静态哈希（Static Hashing）在面对数据量增长时可能导致大量冲突或重建开销大的问题。目标是自动扩容（或收缩）哈希桶、保证查询性能（接近 O(1)）、减少全局重哈希（rehashing）的代价。

Chained Hashing

这是最常见的动态散列方案。DBMS 为哈希表的每个槽维护一个桶的链表。哈希到同一槽的键被简单地插入到该槽的链表中。要查找一个元素，我们先散列到它的桶，然后在链表中扫描查找。

Extendible Hashing

Extendible Hashing 通过引入 目录（Directory）+ 局部桶（Bucket） 的结构来实现 局部扩容、动态调整、按需增长。

目录：

  • 是一个数组，保存指向 Bucket 的指针；
  • 它的大小为 2^global_depth，即目录的大小由全局深度决定；
  • 每个目录项通过哈希函数得到的一部分前缀位定位。

局部桶：

  • 存储实际的数据项；
  • 每个桶有自己的局部深度（local depth）；
  • 表示该桶共享的前缀位数。

插入流程：

  1. 对 key 使用哈希函数，得到一个 hash 值；
  2. 根据 global_depth 取前缀位，定位到目录项；
  3. 找到对应的 Bucket，尝试插入数据：
    • 若 Bucket 未满，直接插入；
    • 若 Bucket 满：
      • 检查 local_depth == global_depth：
        • 是：扩展目录（global_depth+1，目录大小 ×2）；
        • 否：只分裂桶（Bucket Split）；
      • 然后重新分配数据。

缺点：

  • 空间浪费，部分目录项可能指向同一个桶，造成冗余
  • 删除复杂，删除后可能需要合并桶（bucket merge）和收缩目录
  • 实现复杂相比线性哈希实现难度更高，需要维护 local/global depth 和共享桶关系

Linear Hashing

不用一次性重建整个哈希表，而是在数据插入时逐步扩展桶（Bucket），线性地重分布数据，实现渐进扩容。

Linear Hashing 的设计基于：

  • 两个哈希函数：h_i(key) = key mod 2^i 和 h_{i+1}(key) = key mod 2^{i+1}
  • 一个递增的分裂指针 n：表示当前需要分裂扩容的桶编号
  • 一组 桶 Bucket[]

插入过程：

  1. 设当前使用哈希函数 h_i；
  2. 插入 key 时计算 h_i(key)：

Problem #1: How the DBMS represents the database in files on disk.

Database Workload

  • OLTP: Online Transaction Processing （联机事务处理）。特点：高频小型读写操作，事务量大、单次延迟低、更新频繁。场景：网购中用户可以在购物车中添加物品并进行购买，但这些操作只会影响他们的账户。

  • OLAP: Online Analytical Processing （联机分析处理）。特点：大规模复杂查询，主要以读为主，聚合分析、多表联结、批处理操作。场景：网购平台分析从用户购物车和购物历史中收集的所有数据，然后为不同用户推荐不同的广告。

  • HTAP: Hybrid Transaction + Analytical Processing （混合事务分析处理）

Storage Models

DBMS 的存储模型指定它如何在磁盘和内存中物理组织元组。对于不同的存储模型在不同的数据库工作负载中有不同的性能表现。

N-ary Storage Model(NSM)

N-Ary Storage Model，又叫行存储模型（Row Store），是数据库表的传统存储方式。在 NSM 中，每一行（tuple / record）作为一个整体被连续存储在磁盘或内存中，行内包含表的所有列数据。每一行是一个完整的存储单元，所有列的数据被打包存放。

这种方法非常适合 OLTP ，因为在这种情况下请求的写入量很大，访问的大多是单个实体。它之所以理想，是因为只需一次获取就能获得单个元组的所有属性。NSM 页面通常是 4KB 硬件页面的某个恒定倍数。

优点：

  • 快速插入、更新和删除
  • 可使用面向索引的物理存储进行集群

缺点：

  • 不利于扫描表的大部分和/或属性子集。
  • 访问模式的内存位置性很差。
  • 由于单个页面中存在多个值域，因此不适合进行压缩。

Decomposition Storage Model（DSM）

DSM一般被称为：列存储模型（Column Store）。它的核心思想是：把表中的每一列分别独立存储，而不是像 NSM 那样按“行”连续存储。适合OLAP。

优点：

  • 减少每次查询浪费的 I/O 量，因为 DBMS 只读取查询所需的数据。
  • 由于增加了局部性和缓存数据的重复使用，因此查询处理效果更好（更快）。
  • 更好的数据压缩。

缺点：

  • 由于元组分割/缝合，元组查询、插入、更新和删除速度较慢。

快速检索或重新拼接元组的方法：

  • 固定长度偏移。在这种情况下，给定列中的值将与处于相同偏移量的另一列中的值属于同一个元组。因此，列中的每个列中的每个值都必须具有相同的长度。

  • 嵌入式元组 id（不推荐）。为列中的每个属性存储一个元组 ID（例如：主键）。然后，系统还会存储一个映射，告诉它如何跳转到具有该 id 的每个属性。请注意，这种方法的存储开销很大，因为它需要为每个属性条目存储一个元组 ID。

Partition Attributes Across (PAX)

Partition Attributes Across跨属性划分存储，是一种页内列式存储、页间行式存储的模型。

优点：

  • 在传统NSM中，读一列的所有值会带上很多不需要的字段，浪费缓存。而 PAX 的页内列式划分，能够大幅提高 CPU cache 的利用效率。
  • 每页内相同列的数据集中存储，压缩算法（如RLE）效果更好。

Compression

压缩设计原则：

  • 必须产生固定长度的值。快速通过偏移量定位数据，优化CPU缓存访问，兼容字对齐。
  • 支持延迟解压。在查询执行计划中，只有真正需要用到数据（如返回给用户或计算聚合）时，才进行解压。 Late Materialization（延迟物化）
  • 必须是无损压缩。数据完整性保障，不能在存储层丢失精度，任何有损压缩应留给应用层处理。

压缩粒度：

Tuple-level（元组级） 每一行单独压缩 灵活，但压缩率低
Page-level（页级） 每页（通常4KB-8KB）作为压缩单位 常见于行存储，压缩率较高，解压局部性好
Block-level（块级） 多页或特定大小的数据块（如 Parquet 的 RowGroup） 压缩率高，但解压成本较大

可见性

在多线程编程中，可见性（Visibility） 指一个线程对共享数据的修改能够被其他线程及时感知的特性。本质来源于现代计算机的多级缓存架构和编译器的指令重排序优化：

1. 硬件层面：CPU 缓存不一致性

  • 多核 CPU 的缓存结构：每个 CPU 核心有独立缓存（L1/L2），共享 L3 缓存和主内存。
  • 写缓冲区（Store Buffer）：CPU 不会直接写入主存，而是先写入缓冲区，异步刷回内存。
  • 导致问题：线程 A 修改数据后，可能仅更新了本地缓存，未同步到主存，线程 B 读取旧值。

2. 编译器/运行时层面：指令重排序

  • 优化重排序：编译器或 CPU 为了提高性能，可能调整指令顺序（如先读后写）。
  • 导致问题：代码书写顺序 ≠ 实际执行顺序，其他线程观测到不一致状态。

可见性关注的是数据更新的传播，而原子性关注的是操作的不可分割性。

强制可见性的解决方案：

  • 使用原子操作（std::atomic）：原子变量会插入内存屏障（Memory Barrier），阻止重排序并强制缓存同步。
  • 使用原子操作（std::atomic）：锁的加/解锁操作隐含内存屏障。
  • 使用 volatile（有限场景）：阻止编译器优化，但不解决 CPU 缓存一致性问题。volatile 不能替代原子变量或锁，无法保证多线程安全。

std::atomic

std::atomic 是 C++11 引入的用于实现原子操作（Atomic Operation）的模板类，主要用于并发编程。 它能够在无锁（lock-free）或最小锁的情况下，保证线程安全地读写变量，避免数据竞争（Data Race）。

关键特性：

  • 线程安全：多个线程同时访问不会导致未定义行为。
  • 无锁（Lock-Free）：如果底层硬件支持，std::atomic 会使用 CPU 指令实现无锁操作。
  • 内存顺序：支持不同的内存顺序模型（Memory Order Models）。

无锁：是一种并发编程的设计模式，旨在避免使用传统的锁（lock）（如 std::mutex），从而减少线程阻塞、上下文切换，提升程序的并发性能。

CAS（Compare-And-Swap，比较并交换）

CAS（Compare-And-Swap） 是一种用于实现原子操作的并发原语，广泛应用于无锁（lock-free）数据结构中。它通过硬件指令原子地完成三个操作：

  1. 比较（Compare）：检查内存中当前的值是否等于期望值（expected）。
  2. 交换（Swap）：如果相等，则将内存中的值替换为新值（desired）。
  3. 返回结果：返回是否成功交换。

将当前值与expected期望值按位对比，相等就将当前值换为desired值，不相等就将expected值变为当前值。

  • 在一些 CPU 架构（如 ARM）上，weak 版本的 CAS 指令为了优化性能，可能在没有实际数据竞争的情况下也返回失败。
  • 解决方法：在无锁（lock-free）结构中，使用循环重试。

概述

  • 面向对象程序设计（object-oriented programming）的核心思想是数据抽象、继承和动态绑定。

  • 继承

    （inheritance）：

    • 通过继承联系在一起的类构成一种层次关系。
    • 通常在层次关系的根部有一个基类（base class）。
    • 其他类直接或者简介从基类继承而来，这些继承得到的类成为派生类（derived class）。
    • 基类负责定义在层次关系中所有类共同拥有的成员，而每个派生类定义各自特有的成员。
    • 对于某些函数，基类希望它的派生类个自定义适合自己的版本，此时基类就将这些函数声明成虚函数（virtual function）。
    • 派生类必须通过使用类派生列表（class derivation list）明确指出它是从哪个基类继承而来。形式：一个冒号，后面紧跟以逗号分隔的基类列表，每个基类前都可以有访问说明符。class Bulk_quote : public Quote{};
    • 派生类必须在其内部对所有重新定义的虚函数进行声明。可以在函数之前加上virtual关键字，也可以不加。C++11新标准允许派生类显式地注明它将使用哪个成员函数改写基类的虚函数，即在函数的形参列表之后加一个override关键字。

  • 动态绑定

    （dynamic binding，又称运行时绑定）：

    • 使用同一段代码可以分别处理基类和派生类的对象。
    • 函数的运行版本由实参决定，即在运行时选择函数的版本。

定义基类和派生类

定义基类

基类通常都应该定义一个虚析构函数，即使该函数不执行任何实际操作也是如此。

基类通过在其成员函数的声明语句前加上关键字virtual使得该函数执行动态绑定。成员函数没有被声明为虚函数，其解析过程发生在编译器。反之发生在运行时。

除了构造函数和静态成员函数之外，普通的非静态成员函数（包含析构函数）都可以声明为虚函数。

  • 析构函数当然可以 virtual，但它的作用是特殊的（用于实现多态删除）
  • 因为虚函数依赖对象的 vptr，而静态函数不属于对象。
  • 以下不能是虚函数：构造函数、友元函数（不是成员函数）、模板函数实例化时不能改变其“是否虚”属性

如果基类把一个函数声明为虚函数，则该函数在派生类中隐式地也是虚函数

访问控制：

  • protected ： 基类和其派生类还有友元可以访问。
  • private ： 只有基类本身和友元可以访问。

定义派生类

派生类必须通过类派生列表（class derivation list）明确指出它是从哪个基类继承而来。形式：冒号，后面紧跟以逗号分隔的基类列表，每个基类前面可以有一下三种访问说明符的一个：public、protected、private。

继承方式 基类 public成员在派生类中变为 基类 protected成员在派生类中变为 代码外部通过派生类对象访问基类成员
public继承 public protected 可以访问基类的 public成员
protected继承 protected protected 不可访问基类的 public成员
private继承 private private 不可访问基类的 public成员

C++11新标准允许派生类显式地注明它将使用哪个成员函数改写基类的虚函数，即在函数的形参列表之后加一个override关键字。

在派生类对象中含有其基类对应的组成部分，所以能把派生类的对象当成基类对象使用，而且也能将基类的指针或引用绑定到派生类对象中的基类部分上。派生类到基类的类型转换。

在派生类声明之前，其基类必须已经被完整定义，而不能仅仅是前向声明。这是因为编译器需要知道基类的布局和成员。

派生类不能直接初始化从基类继承来的成员，而是必须通过调用基类的构造函数来完成基类部分的初始化。这通常在派生类构造函数的成员初始化列表中进行。首先初始化基类的部分（调用基类的构造函数），然后按声明的顺序依次初始化派生类的成员。

遵循基类的接口：每个类负责定义各自的接口。想要与类的对象交互必须使用该类的接口，即使这个对象是派生类的基类部分也是如此。

静态成员：如果基类定义了一个静态成员，则在整个继承体系中只存在该成员的唯一定义。无论从基类中派生出多少个派生类，对于每个静态成员都只存在一个实例。

派生类的声明：声明中不包含它的派生列表。

C++11新标准提供了一种防止继承的方法，在类名后面跟一个关键字final。

类型转换与继承

可以将基类的指针或引用绑定到派生类对象上。当使用基类的指针或引用时，实际上我们并不清楚该指针或引用所绑定的对象的真实类型。

对象本身不存在动态类型：只有通过指针或引用操作时，静态类型（变量声明时的类型）和动态类型（变量表示的内存中的对象类型）才可能不同。如果直接使用对象本身，其静态类型和动态类型总是一致的

基类的指针或引用的静态类型和动态类型可能不一致。

类型转换规则：

  • 派生类到基类：存在隐式转换（通过指针、引用）。对象之间不存在类型转换。
  • 基类到派生类：不存在隐式转换。必须使用强制类型转换（如 dynamic_cast或 static_cast），且只有当基类指针实际指向派生类对象时才是安全的
  • 和任何其他成员一样，派生类到基类的类型转换也可能会由于访问受限而变得不可行。

虚函数

动态绑定的触发条件：确实只有在通过基类的指针或引用调用虚函数时，才会发生动态绑定（运行时多态）。如果通过对象实例本身调用，则属于静态绑定。

当且仅当对通过指针或引用调用虚函数时，才会在运行时解析该调用，也只有在这种情况下对象的动态类型才有可能与静态类型不同。

一旦某个函数被声明成虚函数，则在所有的派生类中它都是虚函数。

派生类重写虚函数：在派生类中重写虚函数时，virtual关键字是可选的，但函数签名（函数名、参数列表、常量性）必须与基类的虚函数严格匹配。派生类中的虚函数的返回类型也必须和基类函数匹配，存在一个例外，当类的虚函数返回类型是类本身的指针或引用。

override关键字（C++11引入）不改变程序的行为，而是强制编译器进行检查。如果函数被标记为 override但实际上并没有成功重写任何一个基类的虚函数（例如由于拼写错误或参数列表不匹配），编译器将报错。

虚函数也可以使用默认实参。虚函数是动态绑定的，但默认实参是静态绑定的。这意味着，默认实参的值在编译阶段就根据调用该函数的指针或引用的静态类型确定了。最佳实践是：基类和派生类的虚函数应使用相同的默认实参。

使用作用域运算符（::）可以显式指定调用哪个类的函数版本，从而绕过动态绑定。这通常用于特定场景，例如在派生类的虚函数实现中，需要调用基类的版本来完成部分工作。

如果一个派生类虚函数中需要调用它的基类版本，但是没有使用作用域运算符，会导致无限递归。
