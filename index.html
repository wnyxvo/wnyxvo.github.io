核心观点

90% 以上的 CUDA 程序性能瓶颈都在全局内存访问上。理解并优化全局内存访问，是提升 CUDA 程序性能的第一要务。

优化全局内存访问的三大黄金法则：

  1. 合并访存（Coalescing）：让 warp 内的线程访问连续的内存地址
  2. 向量化访问（Vectorization）：使用 float2/float4 等向量类型，一次传输更多数据
  3. 数据复用：将频繁访问的数据缓存到共享内存或寄存器中，减少全局内存访问次数

全局内存的硬件特性

内存架构核心层级

  1. 寄存器 (Registers)：

    • 位置：位于每个流式多处理器（SM）的最顶层。
    • 特点：速度最快，延迟最低，是线程私有的存储空间。

  2. SM 内部本地存储 (SM0 / SM1)

    每个 SM（Streaming Multiprocessor）拥有自己独立的一级存储资源

    • SMEM (Shared Memory)：共享内存，由同一个线程块（Thread Block）内的所有线程共享，速度极快。

    • L1 Cache：一级缓存，每个 SM 独享，用于加速本地和全局内存的访问。

    • Read Only：只读常量缓存。

    • Constant：常量内存缓存。

  3. 全局共享层级 (L2 Cache)

    • 位置：位于 SM 之外。
    • 特点：所有 SM 共用的大容量二级缓存。所有从全局内存（DRAM）读取或写入的数据都会经过 L2 Cache，用以减少对低速显存的直接访问。

  4. 外部显存 (DRAM)

    • 位置：架构的最底层（全局内存）。
    • 特点：容量最大，但访问延迟最高。数据无法直接从 DRAM 传送到寄存器（Registers），必须经过 L2 和 L1/SMEM 层级。

SM (Streaming Multiprocessor)：物理硬件单元。一个 GPU 包含多个 SM。它是执行任务的“工厂”。

Thread Block (线程块)：软件逻辑概念。程序员把总任务切分成多个 Block。

  • 映射关系：一个 Block 一旦被分配，就必须整体驻留在同一个 SM 内部执行，直到全部完成。一个 SM 可以同时驻留多个 Block。

Warp (线程束)：硬件执行的基本单位。

  • 映射关系：**1个 Warp 固定包含 32 个线程 (Threads)**。
  • 运行机制：Block 内部的线程在物理执行时，会被硬件自动切分成一个个 Warp。SM 以 Warp 为单位进行调度，同一个 Warp 内的 32 个线程以 SIMT（单指令多线程） 的方式严格同步执行。

内存事务

在 CUDA 开发中，内存事务（Memory Transaction） 是指 GPU 架构中 L1/L2 缓存与显存（DRAM）之间进行数据传输的最小物理执行单元。

当一个 Warp（32个线程）同时发起内存请求（如读取 float 数组）时，GPU 不会发出 32 次独立的内存请求。相反，GPU 的内存控制器会尝试将这些请求合并（Coalesce）。

  • 物理对齐：GPU 显存是以固定的块（Segment）为单位进行管理的，通常是 32 字节、64 字节或 128 字节。
  • 事务触发：一个内存事务，就是指 GPU 发起了一次读取/写入一个 Segment 的物理操作。
  • 优化目标：用最少次数的内存事务，满足整个 Warp 32 个线程的数据需求。

根据硬件架构，内存事务的尺度通常如下：

  • 32 字节事务：最基础的粒度（对应 8 个 float 或 32 个 char）。无论线程实际请求了多少字节（比如 1 个 char 或 1 个 float），硬件都会从 DRAM 拉取至少 32 字节 的数据放入 L2 缓存。如果只读取了 4 个字节，却加载了 32 字节，这被称为带宽浪费。因此，让相邻线程访问连续内存、实现 100% 的带宽利用率是 CUDA 优化的核心。
  • 128 字节事务：若内核启用了 L1 缓存（如现代 NVIDIA GPU 默认开启）且请求的数据在 L1 缓存中未命中，GPU 加载的粒度会扩大到 128 字节。

全局内存访问数据流

cuda kernel 从 global memory 读取数据的话，数据流 DRAM -> L2 Cache -> L1 cache(可控制)->registers（Thread）。

L1 Cache(可控制) 的意思是，可以通过编译选项手动控制数据是否经过 L1 Cache，L2 Cache 是必须会使用到的。数据是无法直接从 DRAM->registers (原因是这样数据延时会非常大！)

合并访存（Coalescing）

当一个 warp 内的所有线程访问连续的、对齐的内存地址时，硬件可以将这 32 个访问合并成1 个或几个内存事务，这就是合并访存。

高效与低效事务对比

高效：合并访问（1 次 128 字节事务）

32个线程访问连续的 128 字节内存空间，硬件只需发出 1 次事务。

低效：非对齐/跨步访问（多次 32 字节事务）

由于数据未对齐或有跨步（Stride），导致数据分散在多个 Segment 中。

导致额外内存事务的典型场景

在编写代码时，需要极力避免以下导致“内存事务爆炸”的写法：

  1. 非结构化步长访问（Strided Access）：
    • 现象：线程 i 访问 ptr[i * step]。当 step > 1 时，数据在物理上断开。
    • 后果：如果 step 很大，Warp 内 32 个线程可能会触发 32 次 独立事务，带宽利用率跌至 1/32。
  2. 结构体数组（AoS） vs 数组结构体（SoA）：
    • 不要用 AoS：struct Node { float x, y, z; } A[N]; -> 线程访问 A[i].x 时会产生跳跃，引发多次事务。
    • 推荐用 SoA：struct Nodes { float x[N], y[N], z[N]; } A; -> 线程访问 A.x[i] 是完美的连续地址，只需 1 次事务。

如何优化 GPU 访存

为了避免“加载了 32/128 字节却只用了几个字节”造成的带宽浪费，编写 GPU 程序时需要遵循以下两个准则：

  • **合并访问 (Coalesced Access)**：一个 Warp 中的连续线程要访问连续的内存地址（例如 threadIdx.x 对应的线程访问 array[threadIdx.x])。
  • **对齐访问 (Aligned Access)**：每次数据传输的首地址，必须是 32 字节（或 128 字节，取决于缓存机制）的整数倍

合并效率计算公式

在 Nsight Compute 等 GPU 分析工具中，这是最核心的优化指标：$$\text{内存合并效率}=\frac{\text{Warp 请求的实际数据量 (Bytes)}}{\text{GPU 实际触发的内存事务总量 (Bytes)}}\times 100%$$

  • 如果效率是 100%：说明没有带宽浪费。
  • 如果效率只有 12.5%：说明 GPU 花费了 8 倍的带宽去搬运你本来只需要的一点点数据，程序卡在显存瓶颈（Memory Bound）。

baseline

树状折半规约:

潜在的问题:

  • 线程闲置：在规约阶段（for 循环中），随着迭代的进行，参与计算的线程数逐次减半，导致大量线程在整个归约过程中始终处于空闲状态，甚至有部分线程从始至终都没有执行过任何有效计算，是参与计算的线程数过少。

  • 线程束分化 Warp Divergence：

    线程束分化（Warp Divergence） 是 GPU 并行计算（尤其是 CUDA 架构）中一个极其关键的性能瓶颈概念。简单来说，当一个线程束（Warp，通常包含 32 个线程）中的线程在执行代码时，由于逻辑分支（如 if-else、switch 或 for 循环次数不同）走向了不同的指令路径，就会发生分化。

    GPU 使用的是 SIMT（Single Instruction, Multiple Thread），对应的一个 warp 的 32 个线程在同一时刻执行同一条指令。但是如果存在分支代码（if/else），一部分线程走 if，另一部分走 else，会导致执行if时会有一部分线程在空等，warp 内分叉非常严重。

    在一个 warp 中大量的线程是 idle 的

  • 存储体冲突(bank conflict)：

    共享内存被划分为 32 个独立 Bank（SM 为 32），每个 Bank 每周期只能服务 1 次访问

    按 4 字节（int/float） 对齐，地址映射公式：bank_id = (byte_addr / 4) % 32。连续的 4 字节为一组被映射到 Bank 0 到 Bank 31，循环映射。

    示例（__shared__ int s[]）：

    • s[0] → bank 0
    • s[1] → bank 1
    • …
    • s[31] → bank 31
    • s[32] → bank 0（循环）

    当同一个 Warp（32 线程）内多个线程同时访问同一个 Bank 的不同地址时，访问会被串行化，带宽急剧下降

    广播例外：多线程读同一地址 → 硬件广播，无冲突

    当 s == 16 且 tid == 0 时，线程会访问 s[0] 和 s[16]；而当 tid == 1 时，则会访问 s[32] 和 s[48]。这种访问模式导致了 s[0] 和 s[32] 等地址之间出现 bank 冲突，因为它们映射到了相同的共享内存 bank。也就是说不同的线程tid = 0, tid = 1在同一时间访问了同一个bank，也就是s[0]和s[32]所在的bank。

  • 取模运算对于GPU来说消耗太大

index-based addressing

优化点 ：warp divergence 和 modulo 指令开销

还没有解决：shared memory bank conflict

index = 2 * s * tid

本质：不再让所有线程都参与条件判断；而是：只让“可能工作的线程”去访问目标位置。

尽可能让活跃的 thread 都在 同一个 warp 内，减少了线程束分化

shared memory bank conflict 更严重了：

在第一次迭代中，0号线程需要去加载 shared memory 的0号和1号地址，然后写回0号地址。此时，0号 warp 的16号线程需要加载 shared memory 的32和33号地址并且写回32号地址。所以，我们在一个warp内同时访问了一个bank的不同内存地址，发生了2路的 Bank Conflict。

s = 1，warp 0 内 thread0 访问 sdata[0] sdata[1]，thread16 访问 sdata[32] sdata[33]，造成2-way bank conflict

s = 2，warp 0 内 thread0 访问 sdata[0] sdata[2]，thread8 访问 sdata[32] sdata[34]，thread16 访问 sdata[64] sdata[68]，thread24 访问 sdata[96] sdata[100]，造成4-way bank conflict

以此类推，下一次迭代会产生8路的 Bank Conflict，使得整个 Kernel 一直受到 Bank Conflict 的影响。

s = 16，warp 0 内每个 thread 都访问 bank0，出现 32-way bank conflict

Sequential Addressing

s = 1，warp 0 内 thread0 访问 sdata[0] sdata[128]，thread1 访问 sdata[1] sdata[129]…warp0 的线程刚好加载shared memory的一行数据，不会产生 bank conflict

s = 2，warp 0 内 thread0 访问 sdata[0] sdata[64]，thread1 访问 sdata[1] sdata[65]…加载shared memory的一行数据，不会产生 bank conflict

解决 idel 线程：First Add During Load

当前版本的 kernel 浪费了大量的线程。对于第一轮迭代只有128个线程在工作，而第二轮迭代只有64个线程工作，第三轮迭代只有32和线程工作，以此类推，在每一轮迭代中都有大量的线程是空闲的。

数据加载模块进一步优化

之前版本的搬运数据阶段，每个线程都只从全局内存搬运一个元素到共享内存中。 但是实际上我们可以每个线程多读取一点，例如一口气读取两个元素，并且可以直接在本地寄存器里把它们加起来。

注意这里全局下标的步长已经不是blockDim.x，而是对其乘以2。 这就意味着同样数量的线程，v3覆盖的数据是v2的两倍，这意味着Block的数据可以减半。

提升了计算密度。寄存器的带宽远超共享内存，并且没有bank conflict，线程在等待全局数据内存的同时就可以做这件加法。

为什么一次不读4个、8个？

当然可以，而且很多高性能库就是这么干的。但是增加单线程的负载同时也会减少活跃的线程块数，可能降低硬件占用率。因此需要在“每线程工作量”和“并行度”之间找到一个平衡点。v3 的 ×2 只是一个讨巧的起步优化。

展开最后一个 warp

为什么需要展开最后一个 warp？

即使只剩一个 warp，仍然 __syncthreads()，但 warp 内本来就同步，这是 GPU 硬件保证的。warp 内：SIMT lockstep execution、指令天然同步，所以warp 内不需要 __syncthreads()。

从Volta 架构 (SM 7.0)开始，NVIDIA 引入了独立线程调度 (Independent Thread Scheduling)，彻底打破了传统的 “warp 同步执行” 假设

__syncthreads() 非常昂贵

它本质上是block-wide barrier，SM 要：

  • 等待同一 block 内的所有 warp
  • flush dependency
  • scheduler stall

unroll last warp 优化了：

  • 去掉了__syncthreads()
  • 减少了 loop overhead，每次 for 循环也是需要开销的
  • 减少了 branch divergence，s = 16时，warp0 中已有thread0~15是活跃的

为什么用了 volatile？ 防止编译器寄存器缓存。

编译器会做一种非常激进的优化：把频繁访问的共享内存变量缓存在寄存器里。这会导致编译器认为寄存器中的值就是最新值，实际上不是。

加上这个关键字之后，编译器不再对 cache指向的地址做任何寄存器和缓存优化。每一步累加都从共享内存里取最新的数据，算完再立刻写回去。warp 内部的线程能保证它们看到彼此的最新写入，计算也就完全正确了。

在CUDA编程中，volatile核心作用就是强制编译器每次从显存中读取变量，以避免因为优化导致的数据不一致问题。

一般来说它是为了进行跨线程通信与阻止编译器优化。

注意：volatile并不等于同步或者原子操作。如果多个线程并发写，那么仍然会产生数据竞争。它并不能保证原子性与顺序。

CUDA 中的异步API与同步API

CUDA 的 API 分为同步和异步两大类。简单来说，同步 API 会阻塞主机线程直到操作完成，而异步 API 会立即返回，让操作在后台执行。

特性 同步 API 异步 API
阻塞行为 阻塞调用线程，直到操作完成 立即返回，不阻塞调用线程
执行位置 主机线程等待 GPU 完成 GPU 异步执行，主机继续运行
典型函数 cudaMemcpy, cudaMemset cudaMemcpyAsync, cudaMemsetAsync
性能影响 主机和 GPU 不能并行工作 主机和 GPU 可以并行工作
流参数 通常没有流参数 必须有流参数
内存要求 可使用可分页内存 通常需要固定内存

特点：

  1. 阻塞调用：CPU 线程会挂起，直到 GPU 完成该操作
  2. 简单易用：无需担心同步问
  3. 性能较低：CPU 在等待 GPU 时处于空闲状态

为什么异步内存传输必须使用固定内存？

核心原因：DMA 与内存页锁定。异步内存传输通过 DMA 直接在 GPU 和主机内存之间传输数据，绕过 CPU。

  1. DMA 需要物理地址连续性

    • DMA 引擎需要连续的物理内存地址来执行高效的数据传输
    • 常规的 malloc分配的内存是虚拟内存，物理页可能不连续
    • 操作系统随时可能移动物理页（页面交换），DMA 无法处理这种动态变化

  2. 内存页锁定

    cudaMallocHost分配的固定内存会：

    • 锁定物理页：防止操作系统将此内存换出到磁盘
    • 保证物理连续性：DMA 引擎可以获得稳定的物理地址
    • 允许直接访问：GPU 可以直接访问，无需 CPU 介入
    • 异步传输的底层流程
      • 调用 cudaMemcpyAsync
      • DMA 引擎获取固定内存的物理地址
      • DMA 直接从主机内存读取数据到 GPU
      • CPU 可以继续执行其他任务
      • 传输完成时，GPU 产生中断或通过事件通知

  3. 如果使用普通内存会怎样？

Query Plan

  1. 从 SQL 到查询计划：数据库系统接收到 SQL 语句后，并不会直接执行，而是先通过查询优化器将其编译成一个查询计划。这个计划就像一份详细的“执行说明书”。

  2. 操作符树：查询计划是一个树形结构（操作符树）。每个节点代表一个基本操作（称为操作符或代数运算符），例如：

    • 叶子节点：Table Scan（全表扫描）、Index Scan（索引扫描），负责从磁盘中读取数据。
    • 内部节点：Filter（选择，即 WHERE 子句）、Project（投影，即 SELECT 字段）、Join（连接）、Sort（排序）、Aggregate（聚合，如 GROUP BY）。
    • 数据从叶子节点流向根节点，在每个节点进行相应的处理，最终在根节点得到查询结果。

  3. 磁盘导向与缓冲池：因为数据量远大于内存，数据库必须聪明地管理数据在内存和磁盘之间的移动。缓冲池就是核心组件，它充当了磁盘数据在内存中的“缓存”。

    • 当操作符需要处理数据时，它向缓冲池请求特定的页。如果页已在缓冲池中（缓存命中），则直接使用，这是最快的访问方式。
    • 如果页不在缓冲池中（缓存未命中），则需要从磁盘读取，这会带来昂贵的 I/O 成本。
    • 缓冲池需要决定将哪个旧页替换出去（例如使用 LRU 算法）。

  4. 核心目标：最小化 I/O：由于磁盘 I/O 比内存操作慢几个数量级，查询执行算法的设计核心就是尽可能减少磁盘 I/O 次数。这体现在：

    • 访问方法：使用索引（如 B+Tree）来避免全表扫描。
    • 连接算法：使用更高效的算法（如基于哈希的连接、排序-合并连接）来减少中间结果的读写。
    • 利用缓冲池：良好的缓存命中率能极大提升性能。

为了“最小化 I/O”，数据库为不同的操作符设计了特定的算法：

  1. 连接操作：

    • 嵌套循环连接：简单但 I/O 成本可能很高（O(M*N)）。
    • 排序-合并连接：先对两个表按连接键排序，然后进行归并。如果数据能装入内存，效率很高；否则需要外部排序，会产生中间文件的 I/O。
    • 哈希连接：通常效率最高。为其中一个表构建内存哈希表，然后探测另一个表。如果表太大，会采用Grace Hash Join等方法进行分区并溢出到磁盘。

  2. 排序操作：

    • 外部排序：当待排序数据远超内存大小时使用。算法（如外部归并排序）将数据分块排序后写入磁盘，再将有序块归并起来。其 I/O 成本是衡量性能的关键。

  3. 聚合操作：通常使用排序或哈希在分组时进行，同样需要考虑数据是否能放入内存。

数据库查询执行的核心路径：

SQL 查询 -> 查询编译/优化 -> 查询计划（操作符树）-> 由执行引擎调用操作符的具体算法执行 -> 算法依赖缓冲池在内存和磁盘间交换数据 -> 所有设计的首要目标是最小化慢速的磁盘 I/O。

Sorting

关系模型中的表是无序的集合。为了满足 ORDER BY、GROUP BY、JOIN（如排序-合并连接）、DISTINCT等操作对数据有序性的要求，排序是必不可少的。

当数据可以完全放入内存时，可以使用内部排序算法，如快速排序。当数据太大无法放入内存时，需要使用外部排序，例如外部归并排序，它能够将数据溢出到磁盘，并优先使用顺序I/O而不是随机I/O。

Top-N 堆排序

它是对 ORDER BY ... LIMIT N查询的极致优化。

  • 场景：查询只需要结果集中的前 N 条（或后 N 条）记录。
  • 数据结构：使用一个堆（优先队列）。
    • 求前 N 个最小值：使用最大堆。堆顶是堆中最大的元素。新元素如果比堆顶小，则替换堆顶并调整堆。
    • 求前 N 个最大值：使用最小堆。堆顶是堆中最小的元素。新元素如果比堆顶大，则替换堆顶并调整堆。
  • 过程：只需单次扫描数据。对于每条记录，与堆顶元素比较，决定是否替换并调整堆。扫描结束后，堆中剩下的就是 Top-N 结果。
  • 优势：极低的内存占用：只需维护一个大小为 N 的堆，无论总数据量有多大。单次扫描，线性复杂度：算法复杂度为 O(M log N)，其中 M 是总记录数，N 是 LIMIT 值。这比先全排序（O(M log M)）再取前 N 条要高效得多。

外部归并排序 - 通用大数据集排序

这是处理海量数据排序的标准算法，其核心思想是 “分而治之”，分为两个主要阶段：

阶段一：排序阶段

  • 步骤：将大数据集分割成多个小块（称为 Runs），每个小块的大小恰好能放入内存的缓冲池中。
  • 操作：逐个将每个 Run 读入内存，使用高效的内部排序算法（如快速排序）对其进行排序。
  • 输出：将每个在内存中排好序的 Run 作为临时文件顺序地写回磁盘。
  • I/O 优势：无论是读原始数据还是写临时 Run，都追求顺序 I/O，这比随机 I/O 快几个数量级。

阶段二：归并阶段

  • 步骤：将多个已排序的 Run 归并成一个更大的有序文件。由于内存有限，通常采用 K-路归并。
  • 操作：同时打开 K 个已排序的 Run 文件（K 受限于内存缓冲区数量）。为每个文件在内存中维护一个缓冲区，每次从 K 个 Run 的当前值中选出最小（或最大）的一个输出到最终结果，并补充该 Run 的下一个值。
  • 迭代：如果一次 K-路归并后仍然有超过一个 Run，则重复此过程，直到所有数据归并到一个完整的有序文件中。

两路外部归并

核心特点：

  • 每次只归并2个有序段
  • 需要3个缓冲页：2个用于输入，1个用于输出
  • 简单但效率相对较低

过程分解：

排序阶段：读取每个页面 → 内存排序 → 写回有序段
归并阶段：反复两两归并，直到完全有序

I/O成本分析：

  • 趟数（Passes）：1 + ⌈log₂N⌉
  • 总I/O操作：2N × (1 + ⌈log₂N⌉)
  • 示例：N=1000页时，需要1+10=11趟，22,000次I/O操作

通用K路归并排序

N: 文件占用的总页数 (total number of pages in the file)。

B: 内存中可用的缓冲区页数 (number of buffer pages in memory)。

核心优化思想：

  • 利用更多缓冲页：一次性归并K个有序段（而不仅仅是2个）
  • 减少归并趟数：K越大，需要的归并趟数越少
  • 最大化顺序I/O：仍然是批量读写，避免随机访问

策略：

可用缓冲页总数：B ；1个页面用于输出缓冲区 ；剩余B-1个页面用于输入缓冲区（每个归并段占用1个）；∴ 最大归并路数K = B-1

排序阶段：

由于总共有 N 页数据，每次处理 B 页，所以总共需要 N / B 次这样的操作。因为最后一次可能不足 B 页，所以严格来说，会生成： ⌈N / B⌉ 个初始有序顺串，每个顺串的大小（除了最后一个）为 B 页。

归并阶段：

现在有 ⌈N / B⌉ 个有序的顺串在磁盘上。下一步是把它们合并成一个单独的、完全有序的文件。利用缓冲区来同时合并多个顺串。

  • 操作: 在 B 个可用的缓冲区中，必须留出 1 页作为**输出缓冲区 (Output Buffer)**，用来存放归并的结果。
  • 处理: 剩下的 B-1 页缓冲区，则作为**输入缓冲区 (Input Buffers)**，每一页对应一个要被合并的顺串。
  • 归并: 这意味着每一轮归并，最多可以合并 B-1 个顺串。这就是所谓的 (B-1)-way merge。
  • 循环:
    • Pass #1: 将 ⌈N / B⌉ 个顺串，每次 B-1 个进行合并。这一轮结束后，顺串的数量会减少为 ⌈ (⌈N / B⌉) / (B-1) ⌉ 个，但每个顺串的长度变得更长。
    • Pass #2: 对 Pass #1 产生的新顺串，再次进行 (B-1)-way merge。
    • …: 持续这个过程，直到最后只剩下 1 个顺串，即整个文件完全有序。

总趟数 = 初始排序的趟数 () + 归并的趟数。

  • 排序趟数: 占了 1 趟。
  • 归并趟数: 需要计算，从 ⌈N / B⌉ 个初始顺串开始，需要多少轮 (B-1)-way merge 才能合并为 1 个顺串。
    • 这是一个对数问题：$\log_{B-1}(初始顺串数量)$
    • 代入初始顺串数量，归并趟数即为 $\log_{B-1} ⌈N/B⌉$。

推导结果: 将两者相加，总趟数 (Total number of passes) 即为：1 + $\ ⌈log_{B-1} ⌈N/B⌉⌉$

总 I/O 成本: 计算总共发生了多少次磁盘页的读或写。

  • 关键假设: 在每一趟归并躺中，文件中的每一页 (N) 都必须被从磁盘读取一次，然后被写回磁盘一次。每趟成本: N (读) + N (写) = 2N 次 I/O。

推导结果: 总 I/O 成本 = (每一趟的 I/O 成本) × (总趟数) Total I/O Cost = 2N ∙ (# of passes)

将上面推导的趟数公式代入，总成本的完整表达式为： 2N * (1 + $\ ⌈log_{B-1} ⌈N/B⌉⌉$ )

双缓冲优化

双缓冲优化通过预取（prefetching）下一个数据块（run）来减少I/O等待时间。具体来说，当系统正在处理当前数据块时，使用另一个线程在后台预取下一个数据块，并将其存储在第二个缓冲区中。这样，当当前数据块处理完成后，可以立即开始处理下一个数据块，而不必等待I/O。

实现方式：

  • 使用两个缓冲区：一个用于当前处理，一个用于预取下一个数据块。
  • 需要多线程：一个线程处理当前数据块，另一个线程在后台预取下一个数据块。

对比优化

代码特化（Code Specialization）

消除函数调用开销；启用内联优化；更好的指令缓存局部性。

后缀截断（Suffix Truncation）

特别适用于：

  • 长字符串键（VARCHAR、TEXT）
  • 前缀区分度高的数据（如UUID、哈希值）

对于字符串类型的比较，如果键很长，比较操作可能很昂贵。后缀截断优化是：首先比较长字符串的二进制前缀（例如，前几个字节），如果前缀不同，就可以快速得出比较结果；如果前缀相同，再调用完整的字符串比较。这类似于在数据库索引中使用的前缀压缩。

B+树排序

如果需要排序的表已在排序属性上创建了B+树索引，则可利用该索引加速排序过程。

聚簇索引

定义和特点

  • 数据即索引：叶子节点直接包含完整的表数据行
  • 物理有序：数据行按照索引键的顺序物理存储在磁盘上
  • 唯一性：每个表只能有一个聚簇索引

劣势

  • 插入性能：需要维持物理顺序，可能引起页分裂
  • 更新代价：更新索引键可能导致数据移动
  • 灵活性差：每表只能有一个聚簇索引

非聚簇索引

定义和特点

  • 索引与数据分离：叶子节点包含索引键和指向数据行的指针（如聚簇索引主键或物理行指针）
  • 物理无序：数据行物理存储顺序与索引键顺序无关
  • 多索引支持：每个表可以有多个非聚簇索引

核心概念对比

特性 CLUSTERED B+TREE UNCLUSTERED B+TREE
数据存储 索引即数据，叶子节点包含实际数据行 索引与数据分离，叶子节点包含数据指针

Aggregations

聚合操作 的本质是将一组行（元组）根据某个或某几个键（GROUP BY key）分类，然后对每一类计算一个汇总值（标量值），例如 COUNT、SUM、AVG 等。

两种实现路径：数据库管理系统（DBMS）主要通过两种物理操作来实现这个逻辑概念：排序聚合 和 哈希聚合。查询优化器会根据数据量、内存大小、是否需要有序输出等因素选择最佳路径。

排序聚合

原理解释

这种方法非常直观，分为两步：

  1. 排序：首先，将所有数据按照 GROUP BY的键进行排序。这就像把一堆杂乱无章的卡片先按花色和点数排好序。内存排序：如果数据量小，可以直接在内存中用快速排序等算法完成。外存排序：如果数据量超过内存（缓冲区）容量，则使用外部归并排序算法，这是一种分批排序再归并的算法，能够处理海量数据。
  2. 扫描计算：排序后，所有相同键的元组会紧挨在一起。此时，DBMS 只需顺序扫描数据，每当遇到一个新的键，就知道前一个键的所有数据已经处理完毕，可以输出聚合结果了。

特点与优化

  • 输出有序：最大的优点是聚合结果的输出自然就是按照分组键排序的。如果查询后面有 ORDER BY子句，并且排序键和分组键一致，那么这个排序成本就省掉了。
  • 优化策略：“筛选下推”。这是非常重要的优化原则。在执行聚合排序前，应尽早使用 WHERE条件过滤掉不相关的数据行。这样可以显著减少需要排序的数据量，降低 I/O 和 CPU 开销。

拓展：适用场景

  • 当查询最终需要有序输出时（例如后面有 ORDER BY ...）。
  • 当数据本身已经接近有序或有合适的索引时（例如，在分组键上有索引，数据库可能直接使用索引来避免排序）。
  • 当需要产生支持排序的中间结果，以供后续查询操作（如 Merge Join）使用时。

哈希聚合

原理解释

哈希聚合不进行排序，而是利用哈希表的高效查找特性（平均 O(1) 时间复杂度）来实时计算聚合值。

  • 基本思想：DBMS 一边扫描数据，一边维护一个临时哈希表。这个哈希表的键是 GROUP BY的键，值是一个运行值，用于记录当前的聚合状态。
  • 处理过程：对于每一行数据，计算其分组键的哈希值，然后在哈希表中查找：命中：如果找到相同的分组键，则直接更新该键对应的“运行值”（例如，COUNT加 1，SUM加上新值）。未命中：如果没找到，则在哈希表中插入一个新的条目（分组键 -> 初始运行值）。

处理大数据集的分阶段（混合哈希）策略

当数据量巨大，哈希表无法完全放入内存时，DBMS 采用一种“分而治之”的策略，通常包含两个阶段：

阶段一：分区

  • 目标：将大数据集分解成多个能放入内存的小分区。
  • 方法：使用一个哈希函数 h1 将元组分散到不同的磁盘分区中。关键点在于：相同分组键的元组一定会被散列到同一个分区。
  • 内存管理：假设有 B 个内存页（缓冲区），DBMS 会拿出 1 页来读取输入数据，剩下的 B-1 页分别作为 B-1 个分区的输出缓冲区。当某个缓冲区分区页满了，就将其写入磁盘。最终，原始数据被分割成 B-1 个磁盘文件（分区）。

阶段二：再哈希

  • 目标：逐个对分区进行聚合计算。
  • 方法：依次将每个分区从磁盘读入内存。对于分区内的数据，使用另一个不同的哈希函数 h2 在内存中构建一个新的哈希表。然后按照基本的哈希聚合流程处理这个分区内的所有数据。
  • 关键假设：这个策略假设每个分区的大小都能装入内存。由于阶段一确保了同一个分组的所有数据都在同一个分区，因此阶段二可以独立、正确地完成每个分区的聚合计算。

拓展：“运行值”的智慧

  • 哈希表存储的不是最终结果，而是中间状态。这对于不同的聚合函数是不同的：COUNT：运行值就是一个整数，每遇到一个匹配项就加 1。SUM：运行值也是一个数，不断累加。AVG：不能只存一个平均值。运行值通常是一个二元组 (Count, Sum)，最后再计算 Sum / Count。这是一种典型的用空间换准确性的设计。MIN/MAX：运行值就是当前遇到的最小值或最大值。

总结对比与选择策略

特性 排序聚合 哈希聚合
核心步骤 先排序，后扫描 建哈希表，实时更新
输出顺序 有序（按分组键） 无序
内存不足时 使用外部归并排序 使用混合哈希（分区+再哈希）
计算复杂度 O(n log n) **平均接近 O(n)**，更高效
适用场景 1. 需要有序输出 2. 数据已预排序 默认首选，除非需要排序或数据已有序

对于聚合操作，哈希法几乎总是比排序法更高效的，除非数据已经预先排好序，或者查询明确要求有序输出。 因为哈希的平均时间复杂度是线性的，而排序是线性对数的。现代数据库的查询优化器在大多数情况下都会优先选择哈希聚合。

Latches

locks（锁） 和 latches（闩锁） 是两种关键的并发控制机制

特性 Locks (锁) Latches (闩锁)
保护对象 数据库逻辑内容（行、表） 内存物理结构（页、索引节点）
作用范围 事务级别 操作级别（进程、线程）
生命周期 事务期间（秒级） 操作期间（微秒级）
粒度 粗粒度（行/页/表） 细粒度（内存结构）
死锁处理 检测与解决（回滚） 预防（严格顺序）
模式 共享/排他/意向锁等 读/写锁
管理机制 锁管理器 操作系统原语
可见性 用户可见（可查询） 内部实现细节

latch modes:

  • Read mode: 多个线程可以同时读同一个对象；当其他线程在读对象时允许线程获取读锁
  • Write mode: 同一时间只允许一个线程拿到写锁；

latch 要实现的目标：

  • 较小的内存占用
  • 无竞争时快速的执行路径
  • 分布式的闩锁管理机制
  • 避免昂贵的系统调用

latch 实现：

  1. Test-and-Set Spin Latch(TAS)

    TAS就是基于硬件提供的 原子操作（Test-and-Set 指令）实现的一种最经典的自旋锁。当线程无法立即获得锁时，不会进入休眠，而是通过忙等待（循环检测锁是否释放）来争取尽快获得锁。

    用一个布尔变量 lock 表示锁状态：

    • false 表示锁空闲
    • true 表示锁被占用

    简单、高效但不公平，适合短临界区的同步。

    类似地，CAS（Compare-And-Swap / Compare-And-Set）原子操作。它的语义是：如果内存位置的当前值等于预期值，就把它更新为新值；否则，不做任何修改。

    如果变量从 A → B → A，CAS 只看到“还是 A”，可能错误地认为没有变化。解决办法：加上版本号/时间戳，即 CAS+版本号（Tagged Pointer）。

  2. Blocking OS Mutex

    举例 std::mutex，在 GNU libstdc++ 里：

    • std::mutex 通常是 pthread_mutex_t 的轻量包装。
    • pthread_mutex_t 的实现依赖 futex（fast userspace mutex） 系统调用。

    Futex 机制简要：

    • 锁是一个内存中的整数（0 表示解锁，1 表示加锁）。
    • lock() 时，先用 原子 CAS 尝试将 0 → 1。
      • 如果成功 → 获得锁（完全在用户态完成）。
      • 如果失败 → 调用 futex() 系统调用，把线程挂到内核等待队列。
    • unlock() 时，先把值从 1 → 0，再用 futex() 唤醒等待线程。
    • 优点：
      • 没有竞争时，全程用户态（非常快）。
      • 有竞争时，才陷入内核，避免自旋浪费 CPU。

    这就是 “乐观锁 + 内核调度” 的思想。

    非公平锁（谁醒来不保证先到先得），因为这样吞吐量高

  3. Reader-Writer Locks

    举例 std::shared_mutex

    • std::shared_mutex 是基于 pthread_rwlock_t 实现的。

    • pthread_rwlock_t 内部依赖 futex，类似 pthread_mutex_t，但有 reader counter。还依赖pthread_cond_t。

    • Futex 负责挂起/唤醒等待的读者或写者。

    • 公平锁。场景：T1 持有读锁，T2写会被阻塞，此后T3请求读锁不会获得锁，而被阻塞直到T2释放写锁。

  • 多个线程尝试同时修改中同一结点的内容

布隆过滤器

布隆过滤器是一种空间效率极高的概率型数据结构，用于判断一个元素是否在集合中。

  • 可能存在假阳性（false positive）：报告元素存在但实际不存在
  • 绝无假阴性（false negative）：如果报告不存在则一定不存在

工作原理

  1. 数据结构

    • 位数组：长度为 m 的二进制数组（初始全为 0）
    • 哈希函数：k 个独立的哈希函数（h₁, h₂, …, hₖ）

  2. 添加元素

  3. 查询元素

  4. 删除元素

    原始的布隆过滤器不支持删除操作，后续的变种改进可以支持。

变体与改进

计数布隆过滤器

  • 使用计数器数组替代位数组，空间开销会随之增加
  • 添加时计数器+1，删除时-1
  • 支持删除操作

布谷鸟过滤器

工作原理：

  1. 数据结构

    • 桶数组​​：由多个桶组成的数组
    • 指纹存储：每个桶存储固定数量的指纹（fingerprint）
    • 两个哈希函数：h₁ 和 h₂

  2. 指纹生成

  3. 位置计算

  4. 插入算法

    踢出机制（Cuckoo Kick）:

    • 当两个候选桶都满时，随机选择一个桶踢出现有指纹
    • 被踢出的指纹会被重新插入到它的另一个候选位置
    • 最大踢出次数限制（通常500次），超过则视为插入失败

  5. 查询算法

  6. 删除算法

跳表

底层为完整有序链表（存储所有数据），上层为稀疏索引层，每层节点以概率性方式（如抛硬币）决定是否提升到更高层。

概率上：

  • 第一层：存储所有节点
  • 第二层：存储1/2的节点
  • 第三层：存储1/4的节点
  • … …

从最高层索引开始，通过比较节点值快速缩小范围，逐层下降直至底层，实现近似二分查找的效率O(log n) 。

查找

  1. 从最高层开始：从最高层的头节点开始，沿着水平指针向右移动，直到遇到大于目标值的节点或到达该层的末尾。
  2. 向下移动：如果当前层没有找到目标值，则沿着垂直指针向下移动到下一层，重复上述步骤。
  3. 继续查找：在每一层中重复这个过程，直到在最底层找到目标值或确定目标值不存在。

插入

  1. 查找插入位置：首先按照查找过程找到应该插入的位置。
  2. 随机决定层数：使用随机算法决定新节点的层数。例如，可以以50%的概率决定是否将新节点添加到上一层。
  3. 创建新节点并更新指针：在每一层中创建新节点、更新指针，确保新节点被正确地链接到链表中。需缓存查找过程中每层的最后一个前驱节点。

删除

  1. 查找要删除的节点；逐层删除；调整层数
  2. 可以分为逻辑删除和物理删除
    • 设置一个位来表明当前索引是否有效
    • 当确定没有其他线程在使用，就可以物理删除

优劣

  • 优点：比传统的B+树节省空间（不需要预留空间）、插入删除不需要重平衡
  • 缺点：磁盘I/O不友好（跳表的节点随机分布）
