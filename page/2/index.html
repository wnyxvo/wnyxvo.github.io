Task #1 - B+Tree Pages

实现三个页面类来存储 B+Tree 的数据。

  1. BPlusTreePage(Base Page)

    这个类作为后面两个类的基类，存储一些两者都需要的信息，逻辑上是两种类型页面的头部，包括页面类型、当前实际存储的键值对、最大容量。

    GetMinSize()：一般来时需要分别考虑根结点、内部结点和叶子结点，但是结合后续系统的实际逻辑，用于判断结点是否 underflow，只需要返回半满状态时的size就可以了。

  2. BPlusTreeInternalPage(Internal Page)

    这个类对应 B+ 树中的内部结点，比基类多了两个数组分别用于存放K-V对。由于内部结点的特性，子指针的个数比键的个数多一个，key_array_[0] 是无效的。page_id指向的子页面中包含比当前键大与等于的键。

    size_：表示当前页中有效键值对的数量，或者说是有效子指针的个数。

    init()：有默认的参数，是用页面大小 4KB 减去头部信息后计算来的最大容量。对于一个具体的B+树结构需要设置逻辑上的“最大容量”，这就需要在创建页面init()时传入参数。

  3. BPlusTreeLeafPage(Leaf Page)

    这个类对应 B+ 树中的叶子结点，头部信息多了一个字段：指向下一个叶子页面的指针，用于将叶节点串成单向链表。 RID指向实际数据的位置。

ctx 与 锁 的关系

如果某个线程在迭代器获取 RLatch 时失败（说明页面被别的线程 WLatch 住了），那就直接释放当前所有资源，重新从头构造迭代器。这其实就是把乐观锁思想应用到迭代器：失败就自杀并重试。

为什么迭代器遍历时需要失败就自杀？考虑一个场景：线程A遍历叶子节点，线程B执行Remove()。线程A下一个要遍历的叶子节点的写锁被线程B持有；而线程B需要从左兄弟中借出键值对，要请求该叶子节点的写锁。导致死锁。迭代器遍历叶子节点不需要获取叶子节点的父节点。

为什么在 Begin() 也需要处理“读锁拿不到就放弃”？保证最左叶子节点的一致性与稳定性。假设 Begin() 想访问最左叶子 L0，但并发线程正在分裂 L0：

  • 写线程持有 WLatch(L0)，还没更新完成。
  • 这时 Begin() 如果直接用无锁方式返回迭代器：
    • 迭代器拿到的是 L0 的旧内容，下一步 next_page_id 可能错误。
  • 如果 Begin() 等待写锁释放：
    • 会阻塞，吞吐量下降。
  • 如果 Begin() 检测到拿不到 RLatch → 放弃并重启：
    • 等写线程完成后，重启时一定能读到 一致的最左叶子。

遇到的一些细节问题：

  1. 在Insert中，代码里有一段特殊逻辑：如果 root_page_id_ == INVALID_PAGE_ID，会新建 root。
    • 如果两个线程几乎同时看到 INVALID_PAGE_ID，可能会同时创建 root。
    • 但由于更新 header_page->root_page_id_ 时要拿 WritePageGuard，所以最终只有一个 root 会被成功写入，另一个会被覆盖。
    • 不会导致“没有 root”，需要额外逻辑避免浪费掉一个新建的 root page。
  2. 在Insert中，有一个场景：多个节点都想向 leaf L 插入，且此时 L 是安全的，它们都在读 L 父节点，都被路由到 L，拿到了 L 的 page_id。线程A率先拿到写锁，顺利插入后释放写锁，此时 L 已经处于不安全的状态。但是线程 B C 并不知情，它们已经被路由到 L，在等待写锁。这种情况就会导致 L 出现值溢出。

接下来将讨论如何支持 DBMS 的执行引擎从 page 中读写数据。介绍两类结构：Hash Tables(Unordered)、Trees(Ordered)。

Data Structures

在数据库系统中，存储结构的类型可以根据用途划分为以下几大类，它们共同组成了数据库系统的“内部世界”：

  • Internal Meta-Data（内部元数据）：这是数据库系统用于管理自身状态和结构信息的数据。用于记录数据库对象的布局、位置、映射信息等，如页表、页目录等。
  • Core Data Storage（核心数据存储）：这是用来实际存储表中的数据（Tuples）的结构。以页为单位将表的数据组织在磁盘中，如NSM/DSM/PAX、Slotted Page。
  • Temporary Data Structures（临时数据结构）：为了提高查询效率，DBMS 在查询运行时构造的临时结构。如哈希表（用于 hash join 或去重）、排序缓冲区、物化表。这些结构在查询结束后通常会被释放。
  • Table Indices（表索引）：数据库系统为了加速特定查询而维护的辅助数据结构。如 B+ 树索引、哈希索引。索引通常是冗余的，会占用额外空间，但能显著提升性能。

在实现数据结构时还需要考虑以下两个设计决策：数据结构的布局对性能的影响、并发性。

Hash Tables

哈希表实现了一种关联数组抽象类型，能将键映射到值。平均运算复杂度 O(1)，最坏为 O(n)；存储复杂度为 O(n)。即使平均运算复杂度为 O(1)，但仍有常数因子，这在现实世界中非常重要。哈希表中没有访问顺序，即无法按任何特定顺序浏览元素。

哈希表的实现由两部分组成：

  • 哈希函数： 如何将一个大的键空间映射到一个较小的域。在其中要权衡运算速度和冲突率。
  • 哈希方案： 如何处理哈希冲突。在其中要权衡分配哈希表的规模和 get/put 键值的开销

Hash Function

哈希函数接受任何长度的输出，输出固定长度的整数(32bits or 64bits)。DBMS 中不需要使用加密类型的哈希函数（如 SHA-256），只关心速度和冲突率。

现在 state-of-the-art 的哈希函数时Facebook XXHash3。

Static Hash Schemes

Static Hash Schemes 是指哈希表的大小是固定的，并且是已知的。这意味着，如果数据库管理系统的哈希表存储空间用完，就必须从头开始重建一个更大的哈希表，而这是非常昂贵的。通常情况下，新的哈希表是原始哈希表的两倍。

Linear Probe Hashing

对于插入操作，当发生碰撞时，我线性搜索随后的插槽，直到找到开放的插槽为止，必要时会从数组的末尾循环到起始位置。

对于查找操作，可以检查密钥哈希值所对应的插槽，然后进行线性搜索，直到找到所需的条目。如果找到的是空槽，或者遍历了 hashtable 中的所有槽，则说明表中没有该键。请注意，这意味着我们必须在槽中同时存储键和值，以便检查条目是否为所需条目。

对于删除操作：

  • 直接删除会有点问题，如何之前发生过哈希冲突，会有本该映射到此的键值A被映射到了后方，当后续检索A时发现此处为空返回不存在。
  • 另一种方法是在删除条目后移动相邻数据，以填补现在的空槽。不过当键的数量较多时，这种方法的成本极高。
  • 最常见的方法是使用 “墓碑”。我们不是删除条目，而是用一个 “墓碑 ”条目取代它，告诉未来的查找继续扫描。

如何存储键值：

  • 固定长度：直接存储在哈希表页面中。也可选择将密钥的哈希值与之一起存储，以加快比较速度。
  • 不定长度：将键/值数据插入一个单独的临时表中。然后，哈希表将哈希值作为键存储，将指向临时表中相应条目的记录 ID 作为值存储。

如何处理键值不唯一：

  • 独立的链接列表： 不是将值与键一起存储，而是存储一个指向单独存储区的指针，该存储区包含一个包含所有值的链接列表，可能会溢出到多个页面。
  • 冗余键： 更常见的方法是在表中多次存储相同的键。即使我们这样做，线性探测的所有功能仍然有效。

Cuckoo Hashing

Cuckoo Hashing 使用 两个（或多个）哈希函数，每个 key 可以存放在两个可能的位置之一。如果插入的位置被占用了，就“驱逐”（evict）原来的 key，并将其移动到它的另一个位置，可能会引发 连锁搬移。

Cuckoo Hashing 花费 O(1) 的代价查找和删除，但是插入操作可能高代价。

Dynamic Hash Schemes

Dynamic Hashing Schemes（动态哈希方案） 是一类支持数据动态增长（或缩减）的哈希方法，主要为了解决传统静态哈希（Static Hashing）在面对数据量增长时可能导致大量冲突或重建开销大的问题。目标是自动扩容（或收缩）哈希桶、保证查询性能（接近 O(1)）、减少全局重哈希（rehashing）的代价。

Chained Hashing

这是最常见的动态散列方案。DBMS 为哈希表的每个槽维护一个桶的链表。哈希到同一槽的键被简单地插入到该槽的链表中。要查找一个元素，我们先散列到它的桶，然后在链表中扫描查找。

Extendible Hashing

Extendible Hashing 通过引入 目录（Directory）+ 局部桶（Bucket） 的结构来实现 局部扩容、动态调整、按需增长。

目录：

  • 是一个数组，保存指向 Bucket 的指针；
  • 它的大小为 2^global_depth，即目录的大小由全局深度决定；
  • 每个目录项通过哈希函数得到的一部分前缀位定位。

局部桶：

  • 存储实际的数据项；
  • 每个桶有自己的局部深度（local depth）；
  • 表示该桶共享的前缀位数。

插入流程：

  1. 对 key 使用哈希函数，得到一个 hash 值；
  2. 根据 global_depth 取前缀位，定位到目录项；
  3. 找到对应的 Bucket，尝试插入数据：
    • 若 Bucket 未满，直接插入；
    • 若 Bucket 满：
      • 检查 local_depth == global_depth：
        • 是：扩展目录（global_depth+1，目录大小 ×2）；
        • 否：只分裂桶（Bucket Split）；
      • 然后重新分配数据。

缺点：

  • 空间浪费，部分目录项可能指向同一个桶，造成冗余
  • 删除复杂，删除后可能需要合并桶（bucket merge）和收缩目录
  • 实现复杂相比线性哈希实现难度更高，需要维护 local/global depth 和共享桶关系

Linear Hashing

不用一次性重建整个哈希表，而是在数据插入时逐步扩展桶（Bucket），线性地重分布数据，实现渐进扩容。

Linear Hashing 的设计基于：

  • 两个哈希函数：h_i(key) = key mod 2^i 和 h_{i+1}(key) = key mod 2^{i+1}
  • 一个递增的分裂指针 n：表示当前需要分裂扩容的桶编号
  • 一组 桶 Bucket[]

插入过程：

  1. 设当前使用哈希函数 h_i；
  2. 插入 key 时计算 h_i(key)：
    • 若结果 < n，说明这个桶已经被分裂过，改用 h_{i+1}(key)
  3. 把数据插入对应桶中；
  4. 若桶满，则进行分裂操作：
    • 分裂编号为 n 的桶；
    • 将桶中数据按 h_{i+1} 重分布；
    • 分裂指针 n++
    • 若 n == 2^i，则：
      • i++，进入下一轮哈希；
      • n 归零，继续分裂新一轮的桶。

删除可能导致桶删除和分裂指针回移。

Problem #1: How the DBMS represents the database in files on disk.

Database Workload

  • OLTP: Online Transaction Processing （联机事务处理）。特点：高频小型读写操作，事务量大、单次延迟低、更新频繁。场景：网购中用户可以在购物车中添加物品并进行购买，但这些操作只会影响他们的账户。

  • OLAP: Online Analytical Processing （联机分析处理）。特点：大规模复杂查询，主要以读为主，聚合分析、多表联结、批处理操作。场景：网购平台分析从用户购物车和购物历史中收集的所有数据，然后为不同用户推荐不同的广告。

  • HTAP: Hybrid Transaction + Analytical Processing （混合事务分析处理）

Storage Models

DBMS 的存储模型指定它如何在磁盘和内存中物理组织元组。对于不同的存储模型在不同的数据库工作负载中有不同的性能表现。

N-ary Storage Model(NSM)

N-Ary Storage Model，又叫行存储模型（Row Store），是数据库表的传统存储方式。在 NSM 中，每一行（tuple / record）作为一个整体被连续存储在磁盘或内存中，行内包含表的所有列数据。每一行是一个完整的存储单元，所有列的数据被打包存放。

这种方法非常适合 OLTP ，因为在这种情况下请求的写入量很大，访问的大多是单个实体。它之所以理想，是因为只需一次获取就能获得单个元组的所有属性。NSM 页面通常是 4KB 硬件页面的某个恒定倍数。

优点：

  • 快速插入、更新和删除
  • 可使用面向索引的物理存储进行集群

缺点：

  • 不利于扫描表的大部分和/或属性子集。
  • 访问模式的内存位置性很差。
  • 由于单个页面中存在多个值域，因此不适合进行压缩。

Decomposition Storage Model（DSM）

DSM一般被称为：列存储模型（Column Store）。它的核心思想是：把表中的每一列分别独立存储，而不是像 NSM 那样按“行”连续存储。适合OLAP。

优点：

  • 减少每次查询浪费的 I/O 量，因为 DBMS 只读取查询所需的数据。
  • 由于增加了局部性和缓存数据的重复使用，因此查询处理效果更好（更快）。
  • 更好的数据压缩。

缺点：

  • 由于元组分割/缝合，元组查询、插入、更新和删除速度较慢。

快速检索或重新拼接元组的方法：

  • 固定长度偏移。在这种情况下，给定列中的值将与处于相同偏移量的另一列中的值属于同一个元组。因此，列中的每个列中的每个值都必须具有相同的长度。

  • 嵌入式元组 id（不推荐）。为列中的每个属性存储一个元组 ID（例如：主键）。然后，系统还会存储一个映射，告诉它如何跳转到具有该 id 的每个属性。请注意，这种方法的存储开销很大，因为它需要为每个属性条目存储一个元组 ID。

Partition Attributes Across (PAX)

Partition Attributes Across跨属性划分存储，是一种页内列式存储、页间行式存储的模型。

优点：

  • 在传统NSM中，读一列的所有值会带上很多不需要的字段，浪费缓存。而 PAX 的页内列式划分，能够大幅提高 CPU cache 的利用效率。
  • 每页内相同列的数据集中存储，压缩算法（如RLE）效果更好。

Compression

压缩设计原则：

  • 必须产生固定长度的值。快速通过偏移量定位数据，优化CPU缓存访问，兼容字对齐。
  • 支持延迟解压。在查询执行计划中，只有真正需要用到数据（如返回给用户或计算聚合）时，才进行解压。 Late Materialization（延迟物化）
  • 必须是无损压缩。数据完整性保障，不能在存储层丢失精度，任何有损压缩应留给应用层处理。

压缩粒度：

粒度等级 说明 特点
Tuple-level（元组级） 每一行单独压缩 灵活，但压缩率低
Page-level（页级） 每页（通常4KB-8KB）作为压缩单位 常见于行存储，压缩率较高，解压局部性好
Block-level（块级） 多页或特定大小的数据块（如 Parquet 的 RowGroup） 压缩率高，但解压成本较大
Column-level（列级） 某一列的一段连续数据压缩 非常适合列存储，压缩率最高

Columnar Compression

压缩方式 说明 适用场景
Run-Length Encoding (RLE) 连续相同的值用 (Value, Count) 表示 有大量重复值的列（如性别、状态码）
Dictionary Encoding 用一个索引表将字符串替换成短编号，存储编号 字符串或离散值较多的列
Delta Encoding 只存储数值变化的“差值” 连续递增/时间戳/ID字段
Bit-Packing 用尽可能少的二进制位来存储数值，节省空间 数值范围已知、稀疏分布的数据
Bitmap Encoding 为每个不同取值创建一个 bit vector用于表示特定值 取值低基数
  • Bit-Packing ：可以有少量值远大于要压缩成的范围时，使用特殊标识表明要去另一个表中检索。

RAII 风格锁

std::shared_mutex

std::shared_mutex 是 C++17 标准库中引入的一种读写锁，用于在多线程环境中控制对共享资源的访问。它允许：

  • 多个线程同时读取（获取共享锁，也称为读锁）。
  • 一个线程独占写入（获取独占锁，也称为写锁）。

与 std::mutex 不同，std::shared_mutex 提供了更高的并发性，因为读者不会阻塞其他读者。

基本特性

  • 头文件 <shared_mutex>
  • 允许多个线程同时持有读锁（shared_lock）
  • 只允许一个线程持有写锁（unique_lock）
  • 适用于读多写少的场景
  • 不可递归，线程不能多次获取同一种锁
  • 需配合 RAII 包装类，如 shared_lock 和 unique_lock

std::shared_lock

std::shared_lock 是 C++17 标准库中提供的RAII 风格锁管理器，专门用于管理共享（读）锁的生命周期。它与std::shared_mutex或std::shared_timed_mutex类型配合使用，允许多个线程同时获取共享锁，从而实现并发读取。

构造时加锁，析构时解锁（RAII机制）。

轻量级且可移动（可通过 std::move 转移所有权）。

可见性

在多线程编程中，可见性（Visibility） 指一个线程对共享数据的修改能够被其他线程及时感知的特性。本质来源于现代计算机的多级缓存架构和编译器的指令重排序优化：

1. 硬件层面：CPU 缓存不一致性

  • 多核 CPU 的缓存结构：每个 CPU 核心有独立缓存（L1/L2），共享 L3 缓存和主内存。
  • 写缓冲区（Store Buffer）：CPU 不会直接写入主存，而是先写入缓冲区，异步刷回内存。
  • 导致问题：线程 A 修改数据后，可能仅更新了本地缓存，未同步到主存，线程 B 读取旧值。

2. 编译器/运行时层面：指令重排序

  • 优化重排序：编译器或 CPU 为了提高性能，可能调整指令顺序（如先读后写）。
  • 导致问题：代码书写顺序 ≠ 实际执行顺序，其他线程观测到不一致状态。

可见性关注的是数据更新的传播，而原子性关注的是操作的不可分割性。

强制可见性的解决方案：

  • 使用原子操作（std::atomic）：原子变量会插入内存屏障（Memory Barrier），阻止重排序并强制缓存同步。
  • 使用原子操作（std::atomic）：锁的加/解锁操作隐含内存屏障。
  • 使用 volatile（有限场景）：阻止编译器优化，但不解决 CPU 缓存一致性问题。volatile 不能替代原子变量或锁，无法保证多线程安全。

std::atomic

std::atomic 是 C++11 引入的用于实现原子操作（Atomic Operation）的模板类，主要用于并发编程。 它能够在无锁（lock-free）或最小锁的情况下，保证线程安全地读写变量，避免数据竞争（Data Race）。

关键特性：

  • 线程安全：多个线程同时访问不会导致未定义行为。
  • 无锁（Lock-Free）：如果底层硬件支持，std::atomic 会使用 CPU 指令实现无锁操作。
  • 内存顺序：支持不同的内存顺序模型（Memory Order Models）。

无锁：是一种并发编程的设计模式，旨在避免使用传统的锁（lock）（如 std::mutex），从而减少线程阻塞、上下文切换，提升程序的并发性能。

常见操作:

store() 原子存储新值 a.store(42);

**内存顺序模型: **在并发编程中，内存顺序模型（Memory Order Model）定义了多个线程在读写共享内存时的可见性规则和指令重排行为。

内存顺序 关键词 描述 适用场景
memory_order_relaxed 无序模型 不提供顺序保证，只保证原子性 性能优先，对顺序无要求的场景
memory_order_consume 消费模型 只保证数据依赖顺序，编译器不常用 读取依赖少，现代编译器几乎不实现
memory_order_acquire 获取模型 保证之前的读写顺序，但之后的操作可重排 线程读取同步，适用于“获取”数据场景
memory_order_release 释放模型 保证之后的读写顺序，但之前的操作可重排 线程写入同步，适用于“发布”数据场景

  • memory_order_acquire（获取语义）: 在原子操作之后的所有内存读写操作（非原子操作）不会被重排序到该原子操作之前。确保当前线程能看到其他线程通过 release 操作之前的所有修改。
  • memory_order_release（释放语义）: 在原子操作之前的所有内存读写操作（非原子操作）不会被重排序到该原子操作之后。确保当前线程的修改对其他线程的 acquire 操作可见。

同步原理：release 操作会在原子写之前插入释放屏障（防止之前的操作被重排到写之后）。acquire 操作会在原子读之后插入获取屏障（防止之后的操作被重排到读之前）。这种配对形成了一个「同步点」，确保共享数据的可见性。

CAS（Compare-And-Swap，比较并交换）

CAS（Compare-And-Swap） 是一种用于实现原子操作的并发原语，广泛应用于无锁（lock-free）数据结构中。它通过硬件指令原子地完成三个操作：

  1. 比较（Compare）：检查内存中当前的值是否等于期望值（expected）。
  2. 交换（Swap）：如果相等，则将内存中的值替换为新值（desired）。
  3. 返回结果：返回是否成功交换。

将当前值与expected期望值按位对比，相等就将当前值换为desired值，不相等就将expected值变为当前值。

属性 compare_exchange_strong compare_exchange_weak
伪失败（spurious failure） 不会产生伪失败（除非硬件故障） 可能产生伪失败，即使值相同也可能返回 false
是否必须用于循环重试 不需要，失败表示值真的不同 需要，因为可能由于伪失败需要多次重试
性能 略低，因为需要避免伪失败 略高，更适合用于循环中
适用场景 单次交换，例如某些一次性操作 循环重试，例如无锁（lock-free）数据结构

为什么会有伪失败？

  • 伪失败（spurious failure） 是硬件层面或编译器优化造成的现象。
  • 在一些 CPU 架构（如 ARM）上，weak 版本的 CAS 指令为了优化性能，可能在没有实际数据竞争的情况下也返回失败。
  • 解决方法：在无锁（lock-free）结构中，使用循环重试。
场景 推荐使用 原因
一次性交换，性能不敏感 compare_exchange_strong 不会有伪失败，简单明了
高频率交换，需高性能 compare_exchange_weak 可能有伪失败，但整体性能更高
无锁（lock-free）数据结构 compare_exchange_weak + 循环 在循环中重试，优化高并发场景

ABA 问题是 CAS 的常见陷阱:

场景：

  • 线程 T1 读取了共享变量的值 A。
  • 在 T1 进行 CAS 操作之前，另一个线程 T2 将该值从 A → B → A。
  • 当 T1 再次比较时，发现值依然是 A，以为它从未改变，于是继续执行错误逻辑。

解决：

  • 版本号（Version Tagging）：每次修改共享值时，增加一个版本号，确保每次 CAS 比较时同时检查版本号和值。
  • 用指针或高位地址（Tagged Pointer）：在 64 位系统中，指针通常低位对齐，可用高位或额外空间存储版本信息。

实现一个组件来负责跟踪缓冲池中的页面使用情况，用以确定在缓冲池满时该驱逐哪些帧。

LRU-K 算法会淘汰所有帧中后向 k 距离最大的帧。后向 k 距离backward k-distance的计算方式是当前时间戳与前 k 次访问时间戳之间的时间差。历史访问次数少于 k 次的帧的后向 k 距离被赋值为 +inf。如果多个帧的后向 k 距离均为 +inf，则替换器会淘汰 帧（不会在意到底访问了几次）。

C++类设计者的工具-面对对象程序设计

本章内容来自《C++ Primer》、GitHub - applenob/Cpp_Primer_Practice: 搞定 C++👊。C++ Primer 中文版第 5 版学习仓库，包括笔记和课后练习答案。

概述

  • 面向对象程序设计（object-oriented programming）的核心思想是数据抽象、继承和动态绑定。

  • 继承

    （inheritance）：

    • 通过继承联系在一起的类构成一种层次关系。
    • 通常在层次关系的根部有一个基类（base class）。
    • 其他类直接或者简介从基类继承而来，这些继承得到的类成为派生类（derived class）。
    • 基类负责定义在层次关系中所有类共同拥有的成员，而每个派生类定义各自特有的成员。
    • 对于某些函数，基类希望它的派生类个自定义适合自己的版本，此时基类就将这些函数声明成虚函数（virtual function）。
    • 派生类必须通过使用类派生列表（class derivation list）明确指出它是从哪个基类继承而来。形式：一个冒号，后面紧跟以逗号分隔的基类列表，每个基类前都可以有访问说明符。class Bulk_quote : public Quote{};
    • 派生类必须在其内部对所有重新定义的虚函数进行声明。可以在函数之前加上virtual关键字，也可以不加。C++11新标准允许派生类显式地注明它将使用哪个成员函数改写基类的虚函数，即在函数的形参列表之后加一个override关键字。

  • 动态绑定

    （dynamic binding，又称运行时绑定）：

    • 使用同一段代码可以分别处理基类和派生类的对象。
    • 函数的运行版本由实参决定，即在运行时选择函数的版本。

定义基类和派生类

定义基类

基类通常都应该定义一个虚析构函数，即使该函数不执行任何实际操作也是如此。

基类通过在其成员函数的声明语句前加上关键字virtual使得该函数执行动态绑定。成员函数没有被声明为虚函数，其解析过程发生在编译器。反之发生在运行时。

除了构造函数和静态成员函数之外，普通的非静态成员函数（包含析构函数）都可以声明为虚函数。

  • 析构函数当然可以 virtual，但它的作用是特殊的（用于实现多态删除）
  • 因为虚函数依赖对象的 vptr，而静态函数不属于对象。
  • 以下不能是虚函数：构造函数、友元函数（不是成员函数）、模板函数实例化时不能改变其“是否虚”属性

如果基类把一个函数声明为虚函数，则该函数在派生类中隐式地也是虚函数

访问控制：

  • protected ： 基类和其派生类还有友元可以访问。
  • private ： 只有基类本身和友元可以访问。

定义派生类

派生类必须通过类派生列表（class derivation list）明确指出它是从哪个基类继承而来。形式：冒号，后面紧跟以逗号分隔的基类列表，每个基类前面可以有一下三种访问说明符的一个：public、protected、private。

继承方式 基类 public成员在派生类中变为 基类 protected成员在派生类中变为 代码外部通过派生类对象访问基类成员
public继承 public protected 可以访问基类的 public成员
protected继承 protected protected 不可访问基类的 public成员
private继承 private private 不可访问基类的 public成员

C++11新标准允许派生类显式地注明它将使用哪个成员函数改写基类的虚函数，即在函数的形参列表之后加一个override关键字。

在派生类对象中含有其基类对应的组成部分，所以能把派生类的对象当成基类对象使用，而且也能将基类的指针或引用绑定到派生类对象中的基类部分上。派生类到基类的类型转换。

在派生类声明之前，其基类必须已经被完整定义，而不能仅仅是前向声明。这是因为编译器需要知道基类的布局和成员。

派生类不能直接初始化从基类继承来的成员，而是必须通过调用基类的构造函数来完成基类部分的初始化。这通常在派生类构造函数的成员初始化列表中进行。首先初始化基类的部分（调用基类的构造函数），然后按声明的顺序依次初始化派生类的成员。

遵循基类的接口：每个类负责定义各自的接口。想要与类的对象交互必须使用该类的接口，即使这个对象是派生类的基类部分也是如此。

静态成员：如果基类定义了一个静态成员，则在整个继承体系中只存在该成员的唯一定义。无论从基类中派生出多少个派生类，对于每个静态成员都只存在一个实例。

派生类的声明：声明中不包含它的派生列表。

C++11新标准提供了一种防止继承的方法，在类名后面跟一个关键字final。

类型转换与继承

可以将基类的指针或引用绑定到派生类对象上。当使用基类的指针或引用时，实际上我们并不清楚该指针或引用所绑定的对象的真实类型。

对象本身不存在动态类型：只有通过指针或引用操作时，静态类型（变量声明时的类型）和动态类型（变量表示的内存中的对象类型）才可能不同。如果直接使用对象本身，其静态类型和动态类型总是一致的

基类的指针或引用的静态类型和动态类型可能不一致。

类型转换规则：

  • 派生类到基类：存在隐式转换（通过指针、引用）。对象之间不存在类型转换。
  • 基类到派生类：不存在隐式转换。必须使用强制类型转换（如 dynamic_cast或 static_cast），且只有当基类指针实际指向派生类对象时才是安全的
  • 和任何其他成员一样，派生类到基类的类型转换也可能会由于访问受限而变得不可行。

虚函数

动态绑定的触发条件：确实只有在通过基类的指针或引用调用虚函数时，才会发生动态绑定（运行时多态）。如果通过对象实例本身调用，则属于静态绑定。

当且仅当对通过指针或引用调用虚函数时，才会在运行时解析该调用，也只有在这种情况下对象的动态类型才有可能与静态类型不同。

一旦某个函数被声明成虚函数，则在所有的派生类中它都是虚函数。

派生类重写虚函数：在派生类中重写虚函数时，virtual关键字是可选的，但函数签名（函数名、参数列表、常量性）必须与基类的虚函数严格匹配。派生类中的虚函数的返回类型也必须和基类函数匹配，存在一个例外，当类的虚函数返回类型是类本身的指针或引用。

override关键字（C++11引入）不改变程序的行为，而是强制编译器进行检查。如果函数被标记为 override但实际上并没有成功重写任何一个基类的虚函数（例如由于拼写错误或参数列表不匹配），编译器将报错。

虚函数也可以使用默认实参。虚函数是动态绑定的，但默认实参是静态绑定的。这意味着，默认实参的值在编译阶段就根据调用该函数的指针或引用的静态类型确定了。最佳实践是：基类和派生类的虚函数应使用相同的默认实参。

使用作用域运算符（::）可以显式指定调用哪个类的函数版本，从而绕过动态绑定。这通常用于特定场景，例如在派生类的虚函数实现中，需要调用基类的版本来完成部分工作。

如果一个派生类虚函数中需要调用它的基类版本，但是没有使用作用域运算符，会导致无限递归。

C++标准库-并发：promise

本文字数： 889 阅读时长 ≈ 1 分钟

std::promise 是 C++11 引入的标准库类模板，属于并发支持库的一部分，常用于线程间通信。它允许一个线程在将来的某个时间点向另一个线程传递一个值或异常，配合 std::future 使用（负责获取值或异常）。std::promise对象只能使用一次。

主要成员函数

构造函数

  • std::promise()：默认构造函数。
  • std::promise(const std::promise&) = delete：不可复制。
  • std::promise(std::promise&& other)：移动构造函数。

成员函数

  • get_future()：返回与当前 promise 关联的 future 对象，且只能调用一次。
  • set_value(const T& value)：设置共享状态的值，之后 future.get() 可获取该值。
  • set_value_at_thread_exit(const T& value)：在线程退出时设置值。
  • set_exception(std::exception_ptr p)：设置异常，future.get() 调用会抛出该异常。
  • set_exception_at_thread_exit(std::exception_ptr p)：在线程退出时设置异常。

析构函数

  • ~promise()：销毁 promise 对象。如果没有设置值或异常，关联的 future 调用 get() 会抛出 std::future_error。

std::future 的常用方法

  1. get()
    获取与 std::future 关联的结果。该方法会阻塞直到结果可用。
    • 如果计算成功完成，get() 返回结果。
    • 如果任务抛出异常，get() 会重新抛出该异常。
  2. valid()
    检查 std::future 是否有效，即它是否关联着一个有效的异步任务。
  3. wait()
    阻塞当前线程，直到异步操作完成。wait() 不返回结果，仅用于等待计算完成。
  4. wait_for() 和 wait_until()
    这两个方法用于等待异步操作在给定的时间内完成：
    • wait_for() 在指定的时间段内等待结果。
    • wait_until() 在指定的时间点前等待结果。

动态内存

对象的生命周期：

  • 全局对象在程序启动时分配，结束时销毁。
  • 局部对象在进入程序块时创建，离开块时销毁。
  • 局部static对象在第一次使用前分配，在程序结束时销毁。
  • 动态分配对象：只能显式地被释放。

对象的内存位置：

  • 静态内存用来保存局部static对象、类static对象、定义在任何函数之外的变量。
  • 栈内存用来保存定义在函数内的非static对象。
  • 堆内存，又称自由空间，用来存储动态分配的对象。

动态内存和智能指针

C++ 使用 new 和 delete 进行动态内存分配：

问题：

  1. 手动管理内存容易出错，忘记 delete 会导致 内存泄漏。
  2. 异常安全性差，如果 new 分配失败会抛出 std::bad_alloc。
  3. 容易发生悬垂指针（dangling pointer），如 delete 之后仍访问。

解决方案：使用智能指针！智能指针的行为类似常规指针，但负责自动释放所指向的对象。智能指针也是模板，在创建智能指针时需要指定指针指向的类型。

shared_ptr和unique_ptr都支持的操作：

操作 解释
shared_ptr<T> sp unique_ptr<T> up 空智能指针，可以指向类型是T的对象
p 将p用作一个条件判断，若p指向一个对象，则为true
*p 解引用p，获得它**指向的对象本身(T&)**。
p->mem 等价于(*p).mem
p.get() 返回p中保存的指针，内部保存的原始指针 (T*)，要小心使用，若智能指针释放了对象，返回的指针所指向的对象也就消失了。
swap(p, q) p.swap(q) 交换p和q中的指针

shared_ptr 类

作用：多个 shared_ptr 可以共享同一块资源，使用引用计数来管理对象的生命周期。

头文件：#include <memory>

操作 解释

make_shared：

提供的参数列表必须与类型的某个构造函数想匹配。不提供参数，对象就会进行值初始化。

通常，std::shared_ptr<T> 需要存储两部分数据：

  1. 实际的对象 T。
  2. 引用计数控制块（Control Block），它管理引用计数 use_count 以及可能的 deleter。

但shared_ptr 它一次性调用 malloc，分配一个足够大的内存块。

std::make_shared 适用于任何可构造的类型，自动调用构造函数并安全管理内存。

使用动态内存的三种原因：

  • 程序不知道自己需要使用多少对象（比如容器类）。
  • 程序不知道所需要对象的准确类型。
  • 程序需要在多个对象间共享数据。

直接管理内存

用 new 动态分配和初始化对象：

  • new无法为分配的对象命名（因为自由空间分配的内存是无名的），因此是返回一个指向该对象的指针。

  • 在默认情况下（不给参数），动态分配的对象是默认初始化的。也可以使用传统的构造方式，或者列表初始化，或者值初始化。

  • 一旦内存耗尽，会抛出类型是bad_alloc的异常。int *p2 = new (nothrow) int placement new 定位 new

    placement new

    placement new 是一种在用户提供的内存地址上构造对象的机制，它只负责调用构造函数而不负责内存分配。
    使用 placement new 构造的对象需要显式调用析构函数并由用户负责释放内存。
    常用于内存池、标准容器内部实现以及 make_shared 的一次分配优化。

    #include // placement new 所在头文件

    void* raw = operator new(sizeof(T)); // 分配原始内存
    T* obj = new (raw) T(args…); // 构造
    obj->~T(); // 析构
    operator delete(raw); // 释放内存

    析构和释放是两步，不能混。

    placement new 本质是 **一个重载的 operator new**。

    ❌ 错误 1：对 placement new 的对象使用 delete

    ❌ 错误 2：忘记显式析构。会导致资源泄漏。

    ❌ 错误 3：内存对齐不正确。placement new 不会修正对齐问题。

    典型使用场景：内存池 / 对象池；std::vector / std::deque 内部实现；make_shared 的底层机制，一次分配，

    placement new 构造对象和控制块；避免默认构造 + 再赋值（性能优化）；

    构造函数抛异常时：

    • 内存不会被释放
    • 因为 placement new 不拥有内存
    • 使用者必须负责清理

    new (std::nothrow) int 之所以在分配失败时不抛异常，是因为它调用了一个“特殊版本”的 operator new，该版本被标准规定为在失败时返回 nullptr 而不是抛出 std::bad_alloc。

用 delete将动态内存归还给系统。

  • 接受一个指针，指向要释放的对象。和 new 一样执行两个操作：销毁对象，释放内存。
  • delete后的指针称为空悬指针（dangling pointer）。
  • 释放数组时：delete []arr_name

使用 new 和 delete 管理动态内存存在三个常见问题：

  • 1.忘记delete内存。
  • 2.使用已经释放掉的对象。
  • 3.同一块内存释放两次。

shared_ptr和 new 结合使用

接受指针参数的智能指针构造函数是 explicit 的

用来初始化智能指针的普通指针必须指向动态内存，因为智能指针默认使用 delete 来释放它所关联的对象。

shared_ptr<T> p(u) p从unique_ptr u那里接管了对象的所有权；将u置为空
shared_ptr<T> p(q, d) p接管了内置指针q所指向的对象的所有权。q必须能转换为T*类型。p将使用可调用对象d来代替delete。

p.reset(q) 同上

不要混合使用智能指针和普通指针，潜在的风险：

  • 将同一块内存绑定到多个独立创建的 shared_ptr 上
  • 使用已经被 shared_ptr 释放的空悬指针。将一个 shared_ptr 绑定到一个普通指针后就不该再使用内置指针来访问 shared_ptr 所访问的内存了

不要使用 get 初始化另一个智能指针或者为智能指针赋值

智能指针与异常

如果使用智能指针，即使程序块由于异常过早结束，智能指针类也能确保在内存不需要的时候将其释放。

智能指针陷阱：

  • 不用相同的内置指针初始化（或reset）多个智能指针
  • 不delete get()返回的指针。
  • 如果你使用get()返回的指针，记得当最后一个对应的智能指针销毁后，你的指针就无效了。
  • 如果你使用智能指针管理的资源不是new分配的内存，记住传递给它一个删除器。

手撕

shared_ptr 通过“引用计数控制块（control block）”来管理对象生命周期，多个 shared_ptr 共享同一个控制块；当强引用计数降为 0 时析构对象，当弱引用计数也为 0 时释放控制块。

一个 shared_ptr<T> 本质上包含 两样东西：

控制块（control block）里有什么？

条件 行为
strong > 0 对象存活
strong == 0 调用 deleter，销毁对象
weak == 0 且 strong == 0 释放控制块

为什么要有 weak_ptr？

  • 解决 循环引用
  • 不增加 strong count
  • lock() 时才尝试提升为 shared_ptr

make_shared 为什么更高效？

  • 一次内存分配（对象 + 控制块）
  • 更好的 cache locality
  • 异常安全性更强

shared_ptr 线程安全吗？

  • 引用计数操作是线程安全的
  • 对象本身 不是 线程安全
