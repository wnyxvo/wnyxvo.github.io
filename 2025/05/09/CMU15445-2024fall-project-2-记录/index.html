Task #1 - B+Tree Pages

实现三个页面类来存储 B+Tree 的数据。

  1. BPlusTreePage(Base Page)

    这个类作为后面两个类的基类，存储一些两者都需要的信息，逻辑上是两种类型页面的头部，包括页面类型、当前实际存储的键值对、最大容量。

    GetMinSize()：一般来时需要分别考虑根结点、内部结点和叶子结点，但是结合后续系统的实际逻辑，用于判断结点是否 underflow，只需要返回半满状态时的size就可以了。

  2. BPlusTreeInternalPage(Internal Page)

    这个类对应 B+ 树中的内部结点，比基类多了两个数组分别用于存放K-V对。由于内部结点的特性，子指针的个数比键的个数多一个，key_array_[0] 是无效的。page_id指向的子页面中包含比当前键大与等于的键。

    size_：表示当前页中有效键值对的数量，或者说是有效子指针的个数。

    init()：有默认的参数，是用页面大小 4KB 减去头部信息后计算来的最大容量。对于一个具体的B+树结构需要设置逻辑上的“最大容量”，这就需要在创建页面init()时传入参数。

  3. BPlusTreeLeafPage(Leaf Page)

    这个类对应 B+ 树中的叶子结点，头部信息多了一个字段：指向下一个叶子页面的指针，用于将叶节点串成单向链表。 RID指向实际数据的位置。

Task #4 - Concurrency Control

WritePageGuard/ReadPageGuard中已经有读写锁了，为什么还要在 BPlusTreePage中加入读写锁？

这两组锁使用不当会造成死锁。

在BPlusTreePage中加入读写锁，BusTub中已经实现了ReaderWriterLatch。在FindLeafPage()中搜索过程中加读锁时，拥有的是const BPlusTreePage *，默认无法调用非 const成员函数或修改成员变量。需要修改 BPlusTreePage类，将读写锁标记为 mutable，通过 const方法调用锁操作。

乐观锁：在FindLeafPageOptimistic()中

在FindLeafPageWithWrite()中重新设置ctx，防止在函数调用的锁真空期时其他线程更新了B+树。

SEARCH / INSERT / DELETE 都需要读取 header_page，这里拿 Read 就够；只有真正更新 root（分裂/合并）时才需要拿 Write。由于采用了乐观的蟹行锁，需要改动的节点会被锁住。

函数 适用操作 锁策略 特点
FindLeafPageOptimistic SEARCH（读） 乐观路径：先读锁，必要时升级写锁 减少锁竞争，但可能重试
FindLeafPageWithWrite INSERT/REMOVE（写） 悲观路径：直接获取写锁 避免重试开销，但锁粒度大，可能影响并发性

ctx 与 锁 的关系

如果某个线程在迭代器获取 RLatch 时失败（说明页面被别的线程 WLatch 住了），那就直接释放当前所有资源，重新从头构造迭代器。这其实就是把乐观锁思想应用到迭代器：失败就自杀并重试。

为什么迭代器遍历时需要失败就自杀？考虑一个场景：线程A遍历叶子节点，线程B执行Remove()。线程A下一个要遍历的叶子节点的写锁被线程B持有；而线程B需要从左兄弟中借出键值对，要请求该叶子节点的写锁。导致死锁。迭代器遍历叶子节点不需要获取叶子节点的父节点。

为什么在 Begin() 也需要处理“读锁拿不到就放弃”？保证最左叶子节点的一致性与稳定性。假设 Begin() 想访问最左叶子 L0，但并发线程正在分裂 L0：

  • 写线程持有 WLatch(L0)，还没更新完成。
  • 这时 Begin() 如果直接用无锁方式返回迭代器：
    • 迭代器拿到的是 L0 的旧内容，下一步 next_page_id 可能错误。
  • 如果 Begin() 等待写锁释放：
    • 会阻塞，吞吐量下降。
  • 如果 Begin() 检测到拿不到 RLatch → 放弃并重启：
    • 等写线程完成后，重启时一定能读到 一致的最左叶子。

遇到的一些细节问题：

  1. 在Insert中，代码里有一段特殊逻辑：如果 root_page_id_ == INVALID_PAGE_ID，会新建 root。
    • 如果两个线程几乎同时看到 INVALID_PAGE_ID，可能会同时创建 root。
    • 但由于更新 header_page->root_page_id_ 时要拿 WritePageGuard，所以最终只有一个 root 会被成功写入，另一个会被覆盖。
    • 不会导致“没有 root”，需要额外逻辑避免浪费掉一个新建的 root page。
  2. 在Insert中，有一个场景：多个节点都想向 leaf L 插入，且此时 L 是安全的，它们都在读 L 父节点，都被路由到 L，拿到了 L 的 page_id。线程A率先拿到写锁，顺利插入后释放写锁，此时 L 已经处于不安全的状态。但是线程 B C 并不知情，它们已经被路由到 L，在等待写锁。这种情况就会导致 L 出现值溢出。
