可见性

在多线程编程中，可见性（Visibility） 指一个线程对共享数据的修改能够被其他线程及时感知的特性。本质来源于现代计算机的多级缓存架构和编译器的指令重排序优化：

1. 硬件层面：CPU 缓存不一致性

  • 多核 CPU 的缓存结构：每个 CPU 核心有独立缓存（L1/L2），共享 L3 缓存和主内存。
  • 写缓冲区（Store Buffer）：CPU 不会直接写入主存，而是先写入缓冲区，异步刷回内存。
  • 导致问题：线程 A 修改数据后，可能仅更新了本地缓存，未同步到主存，线程 B 读取旧值。

2. 编译器/运行时层面：指令重排序

  • 优化重排序：编译器或 CPU 为了提高性能，可能调整指令顺序（如先读后写）。
  • 导致问题：代码书写顺序 ≠ 实际执行顺序，其他线程观测到不一致状态。

可见性关注的是数据更新的传播，而原子性关注的是操作的不可分割性。

强制可见性的解决方案：

  • 使用原子操作（std::atomic）：原子变量会插入内存屏障（Memory Barrier），阻止重排序并强制缓存同步。
  • 使用原子操作（std::atomic）：锁的加/解锁操作隐含内存屏障。
  • 使用 volatile（有限场景）：阻止编译器优化，但不解决 CPU 缓存一致性问题。volatile 不能替代原子变量或锁，无法保证多线程安全。

std::atomic

std::atomic 是 C++11 引入的用于实现原子操作（Atomic Operation）的模板类，主要用于并发编程。 它能够在无锁（lock-free）或最小锁的情况下，保证线程安全地读写变量，避免数据竞争（Data Race）。

关键特性：

  • 线程安全：多个线程同时访问不会导致未定义行为。
  • 无锁（Lock-Free）：如果底层硬件支持，std::atomic 会使用 CPU 指令实现无锁操作。
  • 内存顺序：支持不同的内存顺序模型（Memory Order Models）。

无锁：是一种并发编程的设计模式，旨在避免使用传统的锁（lock）（如 std::mutex），从而减少线程阻塞、上下文切换，提升程序的并发性能。

常见操作:

函数 描述 示例
load() 原子读取当前值 int x = a.load();
store() 原子存储新值 a.store(42);
exchange() 原子交换值，返回旧值 int old = a.exchange(100);
compare_exchange_weak() 弱式 CAS，可能会意外失败 a.compare_exchange_weak(expected, 10)
compare_exchange_strong() 强式 CAS，持续尝试直到成功 a.compare_exchange_strong(expected, 10)

fetch_sub() 原子减法，返回旧值 a.fetch_sub(1);
fetch_or() 原子或 a.fetch_or(0x01);
fetch_and() 原子与 a.fetch_and(0x01);

**内存顺序模型: **在并发编程中，内存顺序模型（Memory Order Model）定义了多个线程在读写共享内存时的可见性规则和指令重排行为。

内存顺序 关键词 描述 适用场景
memory_order_relaxed 无序模型 不提供顺序保证，只保证原子性 性能优先，对顺序无要求的场景
memory_order_consume 消费模型 只保证数据依赖顺序，编译器不常用 读取依赖少，现代编译器几乎不实现
memory_order_acquire 获取模型 保证之前的读写顺序，但之后的操作可重排 线程读取同步，适用于“获取”数据场景
memory_order_release 释放模型 保证之后的读写顺序，但之前的操作可重排 线程写入同步，适用于“发布”数据场景
memory_order_acq_rel 获取-释放模型 结合 Acquire 和 Release，双向屏障 线程同步，适用于读写混合场景
memory_order_seq_cst 严格顺序一致模型 全局严格顺序，所有线程看到相同的顺序 最安全但最慢，适用于高可靠性场景
  • memory_order_acquire（获取语义）: 在原子操作之后的所有内存读写操作（非原子操作）不会被重排序到该原子操作之前。确保当前线程能看到其他线程通过 release 操作之前的所有修改。
  • memory_order_release（释放语义）: 在原子操作之前的所有内存读写操作（非原子操作）不会被重排序到该原子操作之后。确保当前线程的修改对其他线程的 acquire 操作可见。

同步原理：release 操作会在原子写之前插入释放屏障（防止之前的操作被重排到写之后）。acquire 操作会在原子读之后插入获取屏障（防止之后的操作被重排到读之前）。这种配对形成了一个「同步点」，确保共享数据的可见性。

CAS（Compare-And-Swap，比较并交换）

CAS（Compare-And-Swap） 是一种用于实现原子操作的并发原语，广泛应用于无锁（lock-free）数据结构中。它通过硬件指令原子地完成三个操作：

  1. 比较（Compare）：检查内存中当前的值是否等于期望值（expected）。
  2. 交换（Swap）：如果相等，则将内存中的值替换为新值（desired）。
  3. 返回结果：返回是否成功交换。

将当前值与expected期望值按位对比，相等就将当前值换为desired值，不相等就将expected值变为当前值。

属性 compare_exchange_strong compare_exchange_weak
伪失败（spurious failure） 不会产生伪失败（除非硬件故障） 可能产生伪失败，即使值相同也可能返回 false
是否必须用于循环重试 不需要，失败表示值真的不同 需要，因为可能由于伪失败需要多次重试
性能 略低，因为需要避免伪失败 略高，更适合用于循环中
适用场景 单次交换，例如某些一次性操作 循环重试，例如无锁（lock-free）数据结构

为什么会有伪失败？

  • 伪失败（spurious failure） 是硬件层面或编译器优化造成的现象。
  • 在一些 CPU 架构（如 ARM）上，weak 版本的 CAS 指令为了优化性能，可能在没有实际数据竞争的情况下也返回失败。
  • 解决方法：在无锁（lock-free）结构中，使用循环重试。
场景 推荐使用 原因
一次性交换，性能不敏感 compare_exchange_strong 不会有伪失败，简单明了
高频率交换，需高性能 compare_exchange_weak 可能有伪失败，但整体性能更高
无锁（lock-free）数据结构 compare_exchange_weak + 循环 在循环中重试，优化高并发场景

ABA 问题是 CAS 的常见陷阱:

场景：

  • 线程 T1 读取了共享变量的值 A。
  • 在 T1 进行 CAS 操作之前，另一个线程 T2 将该值从 A → B → A。
  • 当 T1 再次比较时，发现值依然是 A，以为它从未改变，于是继续执行错误逻辑。

解决：

  • 版本号（Version Tagging）：每次修改共享值时，增加一个版本号，确保每次 CAS 比较时同时检查版本号和值。
  • 用指针或高位地址（Tagged Pointer）：在 64 位系统中，指针通常低位对齐，可用高位或额外空间存储版本信息。
