动态内存

对象的生命周期：

  • 全局对象在程序启动时分配，结束时销毁。
  • 局部对象在进入程序块时创建，离开块时销毁。
  • 局部static对象在第一次使用前分配，在程序结束时销毁。
  • 动态分配对象：只能显式地被释放。

对象的内存位置：

  • 静态内存用来保存局部static对象、类static对象、定义在任何函数之外的变量。
  • 栈内存用来保存定义在函数内的非static对象。
  • 堆内存，又称自由空间，用来存储动态分配的对象。

动态内存和智能指针

C++ 使用 new 和 delete 进行动态内存分配：

问题：

  1. 手动管理内存容易出错，忘记 delete 会导致 内存泄漏。
  2. 异常安全性差，如果 new 分配失败会抛出 std::bad_alloc。
  3. 容易发生悬垂指针（dangling pointer），如 delete 之后仍访问。

解决方案：使用智能指针！智能指针的行为类似常规指针，但负责自动释放所指向的对象。智能指针也是模板，在创建智能指针时需要指定指针指向的类型。

shared_ptr和unique_ptr都支持的操作：

操作 解释
shared_ptr<T> sp unique_ptr<T> up 空智能指针，可以指向类型是T的对象
p 将p用作一个条件判断，若p指向一个对象，则为true
*p 解引用p，获得它**指向的对象本身(T&)**。
p->mem 等价于(*p).mem
p.get() 返回p中保存的指针，内部保存的原始指针 (T*)，要小心使用，若智能指针释放了对象，返回的指针所指向的对象也就消失了。
swap(p, q) p.swap(q) 交换p和q中的指针

shared_ptr 类

作用：多个 shared_ptr 可以共享同一块资源，使用引用计数来管理对象的生命周期。

头文件：#include <memory>

shared_ptr独有的操作：

操作 解释
make_shared<T>(args) 返回一个shared_ptr，指向一个动态分配的类型为T的对象。使用args初始化此对象。
shared_ptr<T>p(q) p是shared_ptr q的拷贝；此操作会递增q中的计数器。q中的指针必须能转换为T*
p = q p和q都是shared_ptr，所保存的指针必须能互相转换。此操作会递减p的引用计数，递增q的引用计数；若p的引用计数变为0，则将其管理的原内存释放。
p.unique() 若p.use_count()是1，返回true；否则返回false
p.use_count() 返回与p共享对象的智能指针数量；可能很慢，主要用于调试。

make_shared：

提供的参数列表必须与类型的某个构造函数想匹配。不提供参数，对象就会进行值初始化。

通常，std::shared_ptr<T> 需要存储两部分数据：

  1. 实际的对象 T。
  2. 引用计数控制块（Control Block），它管理引用计数 use_count 以及可能的 deleter。

但shared_ptr 它一次性调用 malloc，分配一个足够大的内存块。

std::make_shared 适用于任何可构造的类型，自动调用构造函数并安全管理内存。

std::make_shared 不能直接用于动态数组：

使用动态内存的三种原因：

  • 程序不知道自己需要使用多少对象（比如容器类）。
  • 程序不知道所需要对象的准确类型。
  • 程序需要在多个对象间共享数据。

直接管理内存

用 new 动态分配和初始化对象：

  • new无法为分配的对象命名（因为自由空间分配的内存是无名的），因此是返回一个指向该对象的指针。

  • 在默认情况下（不给参数），动态分配的对象是默认初始化的。也可以使用传统的构造方式，或者列表初始化，或者值初始化。

  • 一旦内存耗尽，会抛出类型是bad_alloc的异常。int *p2 = new (nothrow) int placement new 定位 new

    placement new

    placement new 是一种在用户提供的内存地址上构造对象的机制，它只负责调用构造函数而不负责内存分配。
    使用 placement new 构造的对象需要显式调用析构函数并由用户负责释放内存。
    常用于内存池、标准容器内部实现以及 make_shared 的一次分配优化。

    #include // placement new 所在头文件

    void* raw = operator new(sizeof(T)); // 分配原始内存
    T* obj = new (raw) T(args…); // 构造
    obj->~T(); // 析构
    operator delete(raw); // 释放内存

    析构和释放是两步，不能混。

    placement new 本质是 **一个重载的 operator new**。

    ❌ 错误 1：对 placement new 的对象使用 delete

    ❌ 错误 2：忘记显式析构。会导致资源泄漏。

    ❌ 错误 3：内存对齐不正确。placement new 不会修正对齐问题。

    典型使用场景：内存池 / 对象池；std::vector / std::deque 内部实现；make_shared 的底层机制，一次分配，

    placement new 构造对象和控制块；避免默认构造 + 再赋值（性能优化）；

    构造函数抛异常时：

    • 内存不会被释放
    • 因为 placement new 不拥有内存
    • 使用者必须负责清理

    new (std::nothrow) int 之所以在分配失败时不抛异常，是因为它调用了一个“特殊版本”的 operator new，该版本被标准规定为在失败时返回 nullptr 而不是抛出 std::bad_alloc。

用 delete将动态内存归还给系统。

  • 接受一个指针，指向要释放的对象。和 new 一样执行两个操作：销毁对象，释放内存。
  • delete后的指针称为空悬指针（dangling pointer）。
  • 释放数组时：delete []arr_name

使用 new 和 delete 管理动态内存存在三个常见问题：

  • 1.忘记delete内存。
  • 2.使用已经释放掉的对象。
  • 3.同一块内存释放两次。

shared_ptr和 new 结合使用

接受指针参数的智能指针构造函数是 explicit 的

用来初始化智能指针的普通指针必须指向动态内存，因为智能指针默认使用 delete 来释放它所关联的对象。

定义和改变shared_ptr的其他方法：

操作 解释
shared_ptr<T> p(q) p管理内置指针q所指向的对象；q必须指向new分配的内存，且能够转换为T*类型
shared_ptr<T> p(u) p从unique_ptr u那里接管了对象的所有权；将u置为空
shared_ptr<T> p(q, d) p接管了内置指针q所指向的对象的所有权。q必须能转换为T*类型。p将使用可调用对象d来代替delete。
shared_ptr<T> p(p2, d) p是shared_ptr p2的拷贝，唯一的区别是p将可调用对象d来代替delete。
p.reset() 若p是唯一指向其对象的shared_ptr，reset会释放此对象。若传递了可选的参数内置指针q，会令p指向q，否则会将p置空。若还传递了参数d，则会调用d而不是delete来释放q。
p.reset(q) 同上
p.reset(q, d) 同上

不要混合使用智能指针和普通指针，潜在的风险：

  • 将同一块内存绑定到多个独立创建的 shared_ptr 上
  • 使用已经被 shared_ptr 释放的空悬指针。将一个 shared_ptr 绑定到一个普通指针后就不该再使用内置指针来访问 shared_ptr 所访问的内存了

不要使用 get 初始化另一个智能指针或者为智能指针赋值

智能指针与异常

如果使用智能指针，即使程序块由于异常过早结束，智能指针类也能确保在内存不需要的时候将其释放。

智能指针陷阱：

  • 不用相同的内置指针初始化（或reset）多个智能指针
  • 不delete get()返回的指针。
  • 如果你使用get()返回的指针，记得当最后一个对应的智能指针销毁后，你的指针就无效了。
  • 如果你使用智能指针管理的资源不是new分配的内存，记住传递给它一个删除器。

unique_ptr 类

手撕

shared_ptr 通过“引用计数控制块（control block）”来管理对象生命周期，多个 shared_ptr 共享同一个控制块；当强引用计数降为 0 时析构对象，当弱引用计数也为 0 时释放控制块。

一个 shared_ptr<T> 本质上包含 两样东西：

控制块（control block）里有什么？

条件 行为
strong > 0 对象存活
strong == 0 调用 deleter，销毁对象
weak == 0 且 strong == 0 释放控制块

为什么要有 weak_ptr？

  • 解决 循环引用
  • 不增加 strong count
  • lock() 时才尝试提升为 shared_ptr

make_shared 为什么更高效？

  • 一次内存分配（对象 + 控制块）
  • 更好的 cache locality
  • 异常安全性更强

shared_ptr 线程安全吗？

  • 引用计数操作是线程安全的
  • 对象本身 不是 线程安全
